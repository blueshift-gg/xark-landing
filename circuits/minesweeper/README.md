# minesweeper circuit

The ZK-minesweeper circuit behind the landing demo, written as a `#![no_std]`
Rust crate for the current xark toolchain (Rust → MIR → R1CS → Groth16). The
9×9 board (`0` = safe, `1` = mine) packs into one field element and is committed
as `hash2(packed, salt)` (Poseidon2). For each reveal the prover publishes a
per-cell bitmask `revealed[]` plus each opened cell's `is_mine` and neighbour
`count`; the circuit constrains all of them against the committed board in a
single proof — a single cell, a flood fill, or a mine click — so opened cells
read correctly while every unopened cell is forced to zero and reveals
nothing. 244 public inputs, 733 R1CS constraints.

The prover (server) supplies **every** public value — `commitment`, `revealed`,
`is_mine` and `count` included — and the circuit asserts each is correct. The verifier
(browser) reads those values back out of the proof's public signals, so the
house cannot move a mine or lie about a cell, and unopened cells stay hidden.

## How the demo uses it

- The board + salt live server-side (`lib/minesweeper.ts`); the
  `/api/minesweeper/*` routes call the `@blueshift-gg/xark-wasm` prover
  in-process, which solves the witness **and** produces the Groth16 proof in one
  call (no separate `nargo` step — xark lowers Rust directly to R1CS).
- `lib/poseidon2.ts` is a TypeScript port of the `xark-poseidon2` gadget, so the
  server can compute the same commitment the circuit constrains and pass it as a
  public input.
- The browser verifies each proof with snarkjs against the committed
  `verification_key.json` before revealing the cell, and checks the commitment
  stays constant across reveals.

Every reveal proves against the same commitment, so the house can't move a mine
or lie about a cell, and unopened cells stay hidden.

## Setup (once)

`xark build` compiles the circuit; `xark setup` generates the Groth16 keys.
`pnpm setup` runs both, then bakes the artifacts the prover loads:

- `circuit.xbc` (self-contained binary build artifact) and `pk.bin` are embedded
  as base64 TS modules (`artifacts/xbc.ts`, `artifacts/pk.ts`, regenerated by
  `scripts/gen-artifacts.mjs`) so the prover is fully self-contained — no
  filesystem and no runtime fetch, which matters on workerd where it runs. The
  `.xbc`/`.bin` are the source of truth; the `.ts` wrappers are build artifacts.
  The wasm derives both the witness solver and the minimized R1CS from the single
  `circuit.xbc`, so no `r1cs.json`/`circuit.json` are needed.
- `verification_key.json` is the snarkjs verifying key the browser verifies with.

```sh
pnpm setup
# ==
# xark build circuits/minesweeper
# xark setup circuits/minesweeper --insecure-dev-mode --deterministic-rng 42
# node scripts/gen-artifacts.mjs   # -> artifacts/{xbc,pk}.ts from circuit.xbc + pk.bin
# cp .../snarkjs-verification_key.json circuits/minesweeper/verification_key.json
```

Regenerating the keys **must** also regenerate `artifacts/{xbc,pk}.ts` (the keys
are keyed to the exact minimized R1CS `circuit.xbc` expands to) and the browser
`verification_key.json`, or proofs will fail to verify.

These are dev keys — forgeable, never for production; a real deployment runs
`xark ceremony`. The prover needs `xark` on PATH (and the pinned nightly it
drives) and a **Node runtime** (not a Cloudflare Worker).
