These three crates are the arithmetic substrate the other gadgets build on — and each is directly
usable in a circuit. `xark-bits` is the bit/word layer; `xark-bignum` is the foreign-field layer
that makes non-native curves possible; `xark-aes` is a full symmetric cipher built on bit
decomposition.

Single-bit operations (booleanity, `to_bits` / `from_bits`, AND/OR/XOR/NOT on one bit) are methods
on `xark::Field`, and so are comparisons, shifts and remainders against a native integer; see
[The xark crate](/docs/reference/language#field). These crates hold the **word** and **limb**
layers.

## `xark-bits` — words and bits

A 32-bit word is `[Field; 32]` in **little-endian** bit order (bit `i` has weight `2^i`), and a
64-bit word is `[Field; 64]`. Get one with `Field::to_bits`, which also range-checks the value, and
turn it back with `Field::from_bits`:

```rust
use xark::{circuit, require_eq, Field, Private, Public};
use xark_bits::{add32, and32, rotr32, xor32};

#[circuit]
pub fn word_ops(a: Private<Field>, b: Private<Field>, out: Public<Field>) {
    let ba = a.to_bits::<32>();
    let bb = b.to_bits::<32>();
    let mixed = add32(rotr32(xor32(ba, bb), 7), and32(ba, bb));
    require_eq(Field::from_bits::<32>(mixed), out);
}
```

| Item | What it does |
| --- | --- |
| `and32`, `or32`, `xor32`, `not32` | Bitwise operations on 32-bit words |
| `and64`, `xor64`, `not64` | The same on 64-bit words |
| `rotr32`, `shr32`, `rotl64`, `rotr64` | Rotations and shifts — rewiring only, no constraints |
| `add32(a, b)`, `add3(a, b, c)` | Addition mod `2^32` of two or three words |
| `reduce::<N>(sum)` | The low 32 bits of a field sum below `2^N`, in `N` rows |
| `xor3`, `maj3`, `chi`, `ch` | One-row bit functions: 3-input XOR, majority, Keccak's χ, SHA-256's choice |
| `xor3_32`, `xor3_64` | `xor3` bit by bit on a word |
| `to_bits64`, `from_bits64` | Split a field element into 64 constrained bits, and recompose |
| `read_n`, `sha256_iv` | Copy word `t` out of a word array; the SHA-256 IV (also BLAKE2s/BLAKE3's) |

The bit functions assume their inputs are bits; `chi`, for one, leaves its output free on a non-bit
input. Feed them words from `to_bits` or from other functions in this crate.

**Cost:** the `word_ops` circuit above is 161 constraints (`examples/word_ops`); `a & b` and
`a ^ b` on two 32-bit values, 128 (`examples/bitwise_basic`).

<Callout title="Stay in the field, reduce once">
SHA-256 mixes several 32-bit words with modular addition. Rather than chaining `add32`, sum the
terms as **field** elements — free — and take the low 32 bits **once** with `reduce::<N>`, where
`N` is the tight bit-width of the sum (a `k`-term 32-bit sum is `< 2^(32 + ⌈log₂ k⌉)`). This is the
general pattern for cheap additions.
</Callout>

## `xark-bignum` — non-native field arithmetic

A BN254 circuit's `Field` is an `Fr` element. To do arithmetic modulo a *different* prime — a
secp256k1 coordinate, an Ed25519 coordinate, an RSA modulus — xark represents the value as
little-endian **limbs**, does the limb-wise arithmetic, and range-checks the carries so no
intermediate wraps the BN254 modulus. The limb buffers go up to 32 limbs of 86 bits, room for
RSA-2048.

`fp!` defines a field-element type from its modulus, with `+`, `-`, `*` and unary `-`:

```rust
use xark::{circuit, require_eq, Field, Private, Public};

// A concrete 256-bit prime field (3 × 86-bit limbs), defined by its modulus alone.
xark_bignum::fp!(El, "41904174945551648470736051755806485464313947085173149");

#[circuit]
pub fn bignum_ops(a: Private<El>, b: Private<El>, out: Public<Field>) {
    let r = a * b + a - b;
    require_eq(r.limbs[0], out);
}
```

On the host each `El` input is one whole number; it is split into limbs for you.

| Item | What it does |
| --- | --- |
| `fp!(Name, "modulus")` | A field type with operators and `.inverse()`, `.sub2()`, `.triple()`, `.reduce()`. Defaults to 3 × 86-bit limbs; `fp!(Name, "0x…", 4, 64)` picks another layout |
| `Bignum<LIMBS, BITS>` | Generic limbed number with `mul`, `add`, `sub`, `neg`, `inverse`, `sub2`, `triple`, `reduce`, `range_check`; the modulus is passed in |
| `mod_mul`, `mod_add`, `mod_sub`, `mod_neg`, `mod_inverse` | The free functions behind them, on `[Field; LIMBS]` |
| `mul_divmod` | `(⌊a·b / m⌋, a·b mod m)`, both constrained |
| `sub2`, `triple_mod`, `reduce_once` | Fused `a − b − c`, `3·v`, and one conditional subtraction |
| `range_check_limbs`, `require_lt`, `is_lt`, `assert_nonzero_limbs` | Limb range checks and comparisons |
| `modulus_limbs`, `modulus_minus_1`, `complement` | `const fn`s that turn a modulus string into limb constants |
| `scalar_to_bits`, `one_hot8`, … | Helpers and curve-specific routines the signature gadgets use |

- Most operations assume canonical operands (`a, b < m`) with range-checked limbs; each function's
  docs give its precondition.
- In `xark_bignum::prelude`, `require_lt` is xark's scalar `require_lt`; call the limb version as
  `xark_bignum::require_lt`.

<Callout type="warn" title="Carry budgets are checked at compile time">
`mod_mul` fails to compile for a `(LIMBS, BITS)` whose column products could wrap the BN254 field.
That is a build error, not a silent wrap — the gadget can't be instantiated with a geometry it
can't keep sound.
</Callout>

| Circuit | Constraints |
| --- | --- |
| `a * b + a - b` over a 3 × 86-bit field (`bignum_ops`) | 2,041 |
| `(a · b) mod m`, 3 × 86 bits, constant modulus (`fp_mul`) | 993 |
| `(a · b) mod m`, 3 × 86 bits, public modulus (`bignum`) | 1,002 |
| `(a · b) mod m`, 24 × 86 bits (`bignum_wide`) | 9,763 |

## `xark-aes` — AES-128/256 in-circuit

The block cipher, CTR mode, and authenticated GCM — to prove a ciphertext encrypts a plaintext you
know, under a key you keep private. AES-128-GCM with 13 bytes of associated data, from
`examples/aes_gcm`:

```rust
use xark_aes::prelude::*;

#[circuit]
pub fn aes_gcm(
    aad: Public<[u8; 13]>, // e.g. a record header — authenticated, not secret
    pt: Private<[u8; 20]>,
    key: Private<[u8; 16]>,
    nonce: Private<[u8; 12]>,
    ct: Public<[u8; 20]>,
    tag: Public<[u8; 16]>,
) {
    let (c, t) = aes128_gcm::<13, 20>(aad, pt, key, nonce);
    require_eq(c, ct);
    require_eq(t, tag);
}
```

A single block is one call: `aes128_constrain(pt, key, ct)`.

| Item | What it does |
| --- | --- |
| `aes128_gcm::<A, N>(aad, pt, key, nonce)`, `aes256_gcm` | GCM (NIST SP 800-38D) with `A` bytes of AAD and a 96-bit nonce; returns `(ciphertext, tag)` |
| `aes128_ctr::<N>(msg, key, nonce)`, `aes256_ctr` | CTR mode: keystream block `b` is `AES(key, nonce ‖ be_u32(b))`, counter from 0 |
| `aes128_encrypt_bytes(pt, key)`, `aes256_encrypt_bytes` | Encrypt one 16-byte block; inputs are bytes, range-checked |
| `aes128_constrain(pt, key, ct)`, `aes256_constrain` | Encrypt one block and require it equal `ct` |
| `aes128_encrypt`, `aes256_encrypt` | One block on bytes already split into bits (`[Field; 8]` each) |
| `gf128_mul`, `bytes_to_gf128`, `gf128_to_bytes` | The GCM field multiply and its bit-order conversions |
| `sbox` | The AES S-box on one byte's bits |
| `key_schedule_byte` | One byte of the expanded AES-128 key (for tests) |

All modes only encrypt; CTR and GCM decryption is the same operation. The lengths `A` and `N` are
compile-time constants. The block cipher is checked against the FIPS-197 known answers and GHASH
against the `ghash` crate; the examples check CTR and GCM against the `aes` and `aes-gcm` crates.

| Circuit | Constraints |
| --- | --- |
| AES-128, one block (`aes`) | 15,360 |
| AES-128-CTR, 20 bytes (`aes_ctr`) | 30,185 |
| AES-256-CTR, 20 bytes (`aes256_ctr`) | 42,273 |
| AES-128-GCM, 20 bytes + 13 bytes AAD (`aes_gcm`) | 185,971 |
| AES-256-GCM, 20 bytes + 13 bytes AAD (`aes256_gcm`) | 209,883 |

Most of GCM's cost is GHASH: each 16-byte block of AAD and ciphertext, and the length block, is one
`gf128_mul`. The S-box is a select over the constant FIPS-197 table, proven sound in Lean over the
rows it emits and checked on all 256 inputs; see
[Formal proofs & audit status](/docs/trust/formal-proofs-and-audit).

## Which layer do I want?

| Task | Layer |
| --- | --- |
| Integer comparison / shift / remainder | native integer inputs, or `Field` against a native integer (`x < 100u32`) |
| Word-level bit manipulation, carry chains, building a custom hash | `xark-bits` |
| Arithmetic modulo a non-BN254 prime (a foreign curve, RSA, big integers) | `xark-bignum` |
| AES encryption or authenticated encryption | `xark-aes` |
| A whole foreign curve | [`xark-curve`](/docs/gadgets/curves), which builds on `xark-bignum` |
