The two gadgets on this page are the ones that turn a hash into a *data structure*: a Merkle path
proves membership without revealing the leaf, and a Pedersen hash gives a commitment whose group
structure makes it additive — the property folding schemes are built on.

## Merkle membership (`xark-merkle`)

```rust
use xark_merkle::prelude::*;

/// The tree's depth: a `const` sizes the path parameters.
pub const DEPTH: usize = 4;

#[circuit]
pub fn merkle(
    leaf: Private<Field>,
    siblings: Private<[Field; DEPTH]>,
    index_bits: Private<[Field; DEPTH]>,
    root: Public<Field>,
) {
    merkle_verify(leaf, siblings, index_bits, root);
}
```

| Item | What it does |
| --- | --- |
| `merkle_verify::<DEPTH>(leaf, siblings, index_bits, root)` | Assert `leaf` is in the tree with this `root`, at the position `index_bits` |
| `merkle_root::<DEPTH>(leaf, siblings, index_bits)` | Fold the path and return the computed root, without checking it |
| `cond_swap(bit, a, b)` | `bit ? (b, a) : (a, b)`, with `bit` constrained to 0 or 1; not in the prelude |

- `siblings` is the authentication path, **leaf level first**.
- `index_bits` is the leaf position, **least significant bit first**: `0` means the running node
  is the left child at that level, `1` the right. Each bit is constrained to 0 or 1 inside the
  gadget, so a prover can't pass some other value to steer the path.
- Nodes are hashed with Poseidon's [`hash2(left, right)`](/docs/gadgets/hashes); the tree must be
  built with the same function.

**Cost:** membership in a depth-4 tree is 957 constraints (`examples/merkle`).

<Callout title="The chain never hashes">
This is the design note behind the shielded examples: the circuit proves that a new root correctly
extends the old one, so an onchain program only has to store roots and verify proofs. Circuit and
chain agree **by construction** instead of by carefully matching two hash implementations. See
[The examples](/docs/guides/examples).
</Callout>

## Pedersen hash (`xark-pedersen`)

```rust
use xark_pedersen::prelude::*;

#[circuit]
pub fn pedersen(m0: Private<Field>, m1: Private<Field>, hx: Public<Field>, hy: Public<Field>) {
    let h = pedersen_hash([m0, m1]);
    require_eq(h[0], hx);
    require_eq(h[1], hy);
}
```

| Item | What it does |
| --- | --- |
| `pedersen_hash(inputs)` | `m₀·G₀ + m₁·G₁` for `mᵢ` in `[1, 2^128)`, returned as the affine Grumpkin point `[x, y]` |

The generators `Gᵢ` are derived by try-and-increment from `SHA256("xark-pedersen:generator:i")`, so
no discrete-log relation between them is known — the security requirement a Pedersen hash needs.
`examples/grumpkin_reference` derives the window tables from them with `ark-grumpkin`.

**Why Grumpkin.** Grumpkin's coordinates are BN254 field elements, the circuit's own field. So a
Pedersen hash returns ordinary field elements — no non-native limb arithmetic, and each group
operation is a handful of constraints. (The same 2-cycle is what makes
[Grumpkin recursion](/docs/reference/folding-and-recursion) cheap.)

**Cost:** the hash of two private scalars checked against a public point is 774 constraints
(`examples/pedersen`).

### Inputs it rejects

Each `mᵢ` must be in `[1, 2^128)`. Zero, larger values, and inputs where `m₀·G₀ = ±m₁·G₁` leave
the circuit unsatisfiable: they are rejected, never forged. `0·G` is the point at infinity, which
the affine form can't express.

`H` is additively homomorphic in `(m₀, m₁)`, which is what lets folding schemes accumulate
instances. Its output is a Grumpkin point, so you can feed it straight into the
[Grumpkin gadgets](/docs/gadgets/curves).

## Choosing between them

| Need | Use |
| --- | --- |
| Membership in a set, cheap to verify | `xark-merkle` (Poseidon) |
| A commitment with homomorphic / algebraic structure | `xark-pedersen` (Grumpkin) |
| A hash inside a Merkle tree whose root is stored onchain | Poseidon — see [the chain never hashes](/docs/guides/examples) |
| Accumulating many statements (folding / IVC) | Pedersen, for the commitment fold |

Both gadgets are unaudited reference implementations. Merkle's conditional swap is proven sound in
Lean over its rows; see [Formal proofs & audit status](/docs/trust/formal-proofs-and-audit).
