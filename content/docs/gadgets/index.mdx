A **gadget** in xark is just a Rust crate that lowers to the same primitive constraints as
hand-written circuit code. There is no per-gadget backend opcode and no separate circuit
language: you add a dependency with `cargo`, call a function inside your `#[circuit]`, and the
compiler inlines the whole thing — every function in the crate, loops unrolled — into your R1CS.

That design is why xark's list of supported hashes and curves is a list of **crates** rather than
a list of built-ins: forking a gadget, pinning a different parameter set, or writing your own is
ordinary Rust work.

## Adding one

```toml
# Cargo.toml
[dependencies]
xark          = { version = "0.2.1", default-features = false }
xark-poseidon = { version = "0.2.1" }
```

```rust
#![cfg_attr(xark, no_std)]
use xark_poseidon::prelude::*;

#[circuit]
pub fn poseidon(a: Private<Field>, b: Private<Field>, out: Public<Field>) {
    require_eq(hash2(a, b), out);
}
```

Most gadgets ship a `prelude` that re-exports their own API **and** the xark essentials, so a
single `use <crate>::prelude::*;` is enough. (The shared libraries — `xark-hash`, `xark-curve`,
`xark-bits` — expose their items at the crate root instead.) Gadget names can collide with a
circuit's entry function — qualify the call (`xark_sha256::sha256(msg)`) when they do, as the
[example circuits](https://github.com/blueshift-gg/xark/tree/master/examples) do.

<Callout title="BN254 is the only field">
Gadgets are written for the BN254 scalar field, xark's default and only target today. If you
override the field with `xark build --field <F>`, gadgets that transcribe field-specific constants
(everything in this section) are not valid. Build without the flag.
</Callout>

## What a gadget costs

Only `variable * variable` emits an R1CS gate. Everything else folds away, and this is what makes
the gadgets affordable:

- **Field constants are free.** Round constants, MDS matrices, and multiplication by a constant
  fold into linear combinations. Poseidon's ARK and MDS layers add **zero** constraints; all 240
  of its gates come from the 80 `x^5` S-boxes.
- **Re-wiring is free.** Rotations, shifts, and lane permutations in the bit-oriented hashes
  (SHA-256's `Σ`/`σ`, Keccak's ρ/π, AES ShiftRows) move bits between array slots and emit nothing.
- **Booleanity is not free.** Every `to_bits::<N>()` range-check costs `N` constraints plus a
  recomposition; the bitwise ops themselves cost roughly one gate per AND (XOR is linear). MiMC's
  keccak-derived round constants and SHA-256's `K[t]` enter sums as constants at no cost.
- **Decompositions are cached per `(value, width)`.** Range-checking the same value twice — or
  range-checking it once and then comparing it — pays only once.

Because a gadget is inlined, the compiler can also [DAG-compress](/docs/reference/serialization)
its repeated function bodies in `circuit.xbc` without changing a single constraint.

The exact counts are per-circuit, not per-gadget: run `xark inspect <crate>` after a build for the
variable / constraint / public-input counts, and `xark profile <crate>` to attribute each
constraint to its source line and function chain.

## Inputs and the host

A `#[circuit]` signature may use the gadget's own types, and the compiler recovers their `Field`
shape from the type:

- `Private<T>` / `Public<T>` are visibility markers; `T` may be `Field`, a fixed array
  `[Field; N]` or `[u8; N]`, a struct of those, or a gadget's compound input type.
- A **byte array** `[u8; N]` becomes `N` field elements, each range-checked to a byte when the
  gadget decomposes it. Bytes are the natural host form for messages.
- A **transparent** gadget type (a signature `Point` / `Signature` / `Scalar`) has a byte form on
  the host and a limb form in-circuit — e.g. a secp256k1 `Point` is `[u8; 64]` (`x ‖ y`, SEC1
  minus the `0x04` tag) on the host and two coordinates in-circuit.
- `Private<Hash>` / `Public<Hash>` pack a 256-bit digest into **two** public inputs instead of 256.
  When a digest is a compile-time constant, use `Digest` instead: it keeps all 256 bits and costs
  no public inputs.

Host inputs are addressed by the **flat leaf names** `xark inspect` prints — `msg[0]`, `path[1]`,
`pubkey.x.limbs[0]` — passed as decimal strings or numbers:

```sh
xark inspect my-circuit          # prints the exact public-input order and names
xark prove my-circuit --inputs '{"msg[0]": 97, "msg[1]": 98, "msg[2]": 99, "digest.hi": 0, "digest.lo": 0}'
```

<Callout type="info" title="Start from a worked example">
Each gadget has one or more runnable circuits under
[`examples/`](https://github.com/blueshift-gg/xark/tree/master/examples) — `sha256`, `poseidon`,
`secp256k1_ecdsa`, `ed25519`, `merkle`, `aes_gcm`, `grumpkin_ivc`, and the rest. They are the
fastest way to see a gadget's host input form in practice.
</Callout>

## Writing your own

Because a gadget is library code, the test for "can this be a gadget?" is the
[supported subset](/docs/reference/supported-subset): fixed-size arrays, constant loop bounds and
indices, `Field` arithmetic, and calls to other gadgets. Hashes and curves are not special-cased;
they are just code that respects those rules.
