Every hash gadget is a plain Rust crate that xark builds into your circuit. They all follow the
same shape: hash the message, then `require_eq` the digest against the public value. The
differences are the input form (bytes or field elements), the message length limits, and the
constraint cost.

## The digest types (`xark-hash`)

`xark-hash` holds the 256-bit digest types the byte-oriented hashes share. You rarely depend on it
directly: `xark-sha256`, `xark-keccak`, `xark-blake2s` and `xark-blake3` re-export `Hash` from their
preludes (`xark-sha256` also `Digest`).

| Item | What it does |
|---|---|
| `Hash` | A 256-bit hash as two field elements, `hi` and `lo` (16 bytes each, big-endian). As `Public<Hash>` it costs 2 public inputs, not 256. On the host it's a plain `[u8; 32]`. |
| `Hash::pack(bits)` | Build a `Hash` from 256 bits in big-endian weight order, to give your own hash gadget the same public form. |
| `Hash::to_fields()` | The two field elements `[hi, lo]`, to hash or bind them. |
| `Digest` | All 256 bits of a SHA-256 output. Use it to compare against a constant digest baked into the circuit. |
| `Digest::require_eq(other)` | Constrain two digests equal, bit for bit. |

`require_eq` between a raw gadget output and a `Hash` works for SHA-256's output and Keccak's;
BLAKE outputs use the `Blake256` wrapper from their own crates. A `Public<Digest>` would be 256
public inputs: use `Hash` for a digest that changes per proof.

## SHA-256 (`xark-sha256`)

```rust
use xark_sha256::prelude::*;

#[circuit]
pub fn sha256(msg: Private<[u8; 3]>, digest: Public<Hash>) {
    // Qualified: the entry fn shares the gadget's name.
    require_eq(xark_sha256::sha256(msg), digest);
}
```

To compare against a digest fixed at compile time, use `Digest` instead:

```rust
let expected: Digest = SHA256_ABC.into();
Digest::from(sha256(msg)).require_eq(expected);
```

| Item | What it does |
|---|---|
| `sha256::<N_BYTES>(msg)` | SHA-256 of `N_BYTES` bytes, with padding and multi-block chaining. Each byte is range-checked. Returns 8 words of 32 little-endian bits. |
| `sha256_block(w)` | One compression from the standard IV, on 16 message words you have already laid out. No padding. |
| `compress(h_in, w)` | The compression function, from any 8-word chaining value. |
| `h0()` | The SHA-256 initial hash value, as field constants. |

The message length is a compile-time constant: a circuit has a fixed size. Its output matches the
`sha2` crate.

**Cost:** a 3-byte message checked against a public `Hash` is 16,472 constraints (`examples/sha256`);
against a constant `Digest`, 16,216 (`examples/sha256_consume`).

## Keccak-256 (`xark-keccak`)

```rust
use xark_keccak::prelude::*;

#[circuit]
pub fn keccak256(msg: Private<[u8; 3]>, digest: Public<Hash>) {
    require_eq(xark_keccak::keccak256(msg), digest);
}
```

| Item | What it does |
|---|---|
| `keccak256::<N_BYTES>(msg)` | Keccak-256 of `N_BYTES` bytes, with Ethereum's `0x01` padding. Each byte is range-checked. Returns 4 lanes of 64 little-endian bits. |
| `keccak256_block(block)` | Keccak-256 of one rate block (17 lanes) you have already padded. |
| `keccak_f(state)` | The Keccak-f[1600] permutation: 24 rounds on 25 lanes. |

This is Keccak-256 as Ethereum uses it, matching `sha3::Keccak256` — not NIST SHA3-256, which pads
with `0x06`. `keccak_f` and `keccak256_block` expect every input bit to be constrained to 0 or 1
already; `keccak256` does that for you.

**Cost:** a 3-byte message checked against a public `Hash` is 89,375 constraints
(`examples/keccak256`) — the most expensive hash here, so prefer Poseidon for tree-shaped work.

## BLAKE2s (`xark-blake2s`) and BLAKE3 (`xark-blake3`)

```rust
use xark_blake2s::prelude::*; // or xark_blake3::prelude::*

#[circuit]
pub fn blake2s(msg: Private<[u8; 3]>, digest: Public<Hash>) {
    // `Blake256` selects BLAKE's little-endian word order for the comparison.
    require_eq(Blake256(xark_blake2s::blake2s(msg)), digest);
}
```

| | BLAKE2s | BLAKE3 |
| --- | --- | --- |
| one-shot hash | `blake2s::<N_BYTES>(msg)`: unkeyed BLAKE2s-256 | `blake3::<N_BYTES>(msg)`: the root hash, `N_BYTES <= 1024` |
| one block | `blake2s_hash_one_block::<LEN>(input_words)`, `LEN <= 64` bytes, the rest zero | `blake3_hash_one_block::<LEN>(input_words)`, `LEN <= 64` bytes, the rest zero |
| compression | `compress(...)`, with counter and final-block flag | `compress(...)`, with counter, block length and flags |
| matches | `blake2`'s `Blake2s256` | `blake3`'s `hash` |
| cost (3-byte message vs a public `Hash`) | 20,066 constraints | 13,780 constraints |

Both range-check each byte and return 8 words of 32 little-endian bits. Wrap the output in
**`Blake256`** before comparing it with a `Hash`. Keyed hashing is not provided, and BLAKE3 messages
over 1024 bytes (its multi-chunk tree mode) are not supported.

## MiMC (`xark-mimc`)

```rust
use xark_mimc::prelude::*;

#[circuit]
pub fn mimc_gadget(x: Private<Field>, k: Private<Field>, h: Public<Field>) {
    require_eq(mimc(x, k), h);
}
```

| Item | What it does |
|---|---|
| `mimc_bn254::<N>(inputs)` | The multi-input MiMC-BN254 hash (a Feistel / Miyaguchi–Preneel sponge). Matches Noir's `mimc_bn254`. |
| `mimc(x, k)` | The MiMC-p/p permutation keyed by `k`: 91 rounds of `(state + k + C[i])^7`, then a key addition. Matches Noir's `mimc`. |

This is a port of [Noir's MiMC](https://github.com/noir-lang/mimc), compatible with circomlib —
use it when you need digests that match a circom or Noir system already using MiMC. A test checks it
against Noir's known answer:

```text
mimc_bn254([12, 45, 78, 41])
  = 18226366069841799622585958305961373004333097209608110160936134895615261821931
```

## Poseidon (`xark-poseidon`) and Poseidon2 (`xark-poseidon2`)

These are the field-native hashes: inputs and output are `Field` elements, no byte packing, so they
cost a few hundred constraints where a byte hash costs thousands. They are the right choice for
Merkle trees and in-circuit commitments.

```rust
use xark_poseidon::prelude::*;

#[circuit]
pub fn poseidon(a: Private<Field>, b: Private<Field>, out: Public<Field>) {
    require_eq(hash2(a, b), out);
}
```

| | Poseidon | Poseidon2 |
| --- | --- | --- |
| 2-to-1 compression | `hash2(a, b)` = `permute([0, a, b])[0]` | `hash2(a, b)` = `poseidon2_perm([a, b, 0])[0]` |
| sponge | `hash::<N>(inputs)` | `hash::<N>(inputs)` |
| permutation | `permute(state)` | `poseidon2_perm(state)` |
| on the host | — | `xark_poseidon2::native`: every function over `ark_bn254::Fr`, plus `hash_slice` |
| `hash::<5>` cost | 717 constraints | 721 constraints |

Both are width 3 with an `x^5` S-box, 8 full and 56 partial rounds, and the Horizen Labs
constants. The sponge has rate 2 and capacity 1, seeded with `N`, so inputs of different lengths
don't collide (`hash([a]) != hash([a, 0])`). `hash2` of two private elements checked against a
public output is 238 constraints (`examples/poseidon`).

Poseidon and Poseidon2 give different digests. Pick one and use the same one wherever the digest
is computed — and if you also need it outside the circuit, pick Poseidon2: its `native` module runs
the same implementation on the host, so a wallet or test computes the digest a circuit commits to
without a second copy.

```rust
use xark_poseidon2::native::{hash, Fr};

let commitment: Fr = hash([Fr::from(7u64), Fr::from(11u64)]);
```

## Which hash should I use?

| Need | Pick |
| --- | --- |
| Merkle trees, commitments, anything in-circuit and field-native | **Poseidon2** (or Poseidon) |
| Verify an existing SHA-256 digest (Bitcoin, TLS, `sha2`) | `xark-sha256` |
| Verify an existing Keccak-256 / Ethereum digest | `xark-keccak` |
| Verify `blake2`/`blake3` data | `xark-blake2s` / `xark-blake3` |
| Circom/Noir-compatible MiMC | `xark-mimc` |

All of them run inside the circuit, so a proof verifies the hash *by recomputing it in R1CS* —
there is no "hash oracle" the chain has to trust. That is also the design note behind the
[shielded examples](/docs/guides/examples): the chain never hashes, because the circuit already
did.
