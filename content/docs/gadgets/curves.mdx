Two crates carry the elliptic-curve layer. `xark-grumpkin` gives you native-field Grumpkin
arithmetic ready to call; `xark-curve` is the macro library that **emits** a curve gadget over a
non-native field from its constants, and is how `xark-secp256k1`, `xark-secp256r1`, and
`xark-ed25519` are built.

## Grumpkin (`xark-grumpkin`)

```rust
use xark_grumpkin::prelude::*;

#[circuit]
pub fn grumpkin(
    s0: Public<Field>,
    s1: Public<Field>,
    p0: Public<Affine>,
    p1: Public<Affine>,
    r: Public<Affine>,
) {
    let out = multi_scalar_mul([s0, s1], [[p0.x, p0.y], [p1.x, p1.y]]);
    require_eq(out[0], r.x);
    require_eq(out[1], r.y);
}
```

This checks `r = s0·p0 + s1·p1` for 128-bit scalars, in 1,569 constraints (`examples/grumpkin`).

| Item | What it does |
| --- | --- |
| `ec_add(p, q)`, `ec_double(p)` | Incomplete affine addition (`p ≠ ±q`) and doubling |
| `scalar_mul(bits, p)` | `m·p` for a 128-bit scalar given as little-endian bits; `p` is a witness point |
| `multi_scalar_mul(scalars, points)` | `s₀·P₀ + s₁·P₁` for two 128-bit scalars |
| `wide_scalar_mul(s, p)` | `s·p` for a full-width (254-bit) `WideScalar` |
| `decompose(x)` | `x` as 128 little-endian bits, constrained |
| `enforce_on_curve(p)` | Assert `p` is on Grumpkin (`y² = x³ − 17`) |
| `Affine`, `WideScalar`, `Instance` | Circuit inputs: a point; a scalar as two 127-bit limbs; a committed relaxed-R1CS (Nova) instance |
| `N_BITS`, `K` | The scalar bit length (128) and the number of pairs in `multi_scalar_mul` (2) |

Four full-width `wide_scalar_mul`s summed with three `ec_add`s are 8,188 constraints
(`examples/grumpkin_ipa`).

**Why this is cheap.** Grumpkin and BN254 form a 2-cycle: Grumpkin's coordinates are BN254 field
elements, xark's native `Field`. So every group operation is a handful of native constraints — no
non-native limb emulation. That is the whole reason the
[folding work](/docs/reference/folding-and-recursion) is affordable: a full Nova fold step
verifies in-circuit in **~6k constraints**, versus millions for non-native curve arithmetic.

**Edge cases.** `ec_add` and `ec_double` can't represent the point at infinity, so the scalar
multiplications run an **offset** double-and-add: the accumulator starts at a fixed non-identity
point, and the offset is removed at the end by a precomputed correction. They reject a result at
infinity (for example a zero scalar), and `multi_scalar_mul` rejects `P₀ = ±P₁`. A prover can't
forge a result at these edges; an honest prover with such inputs can't prove.

**Scalars come in as inputs.** Grumpkin's scalar field is not the circuit's field, so arithmetic on
scalars (such as Fiat–Shamir challenges) can't be done soundly here.

<Callout title="Need the point at infinity?">
For a fold whose accumulator can legitimately start at `∞` (a fresh Nova instance has
`comm_E = ∞`), use the **flagged-affine complete addition** in `examples/grumpkin_complete_add`:
points are `[x, y, inf]`, and `P+∞`, `∞+Q`, `P+(−P) = ∞`, `P+P`, and generic `P+Q` are all
resolved branch-free. It costs 24 constraints.
</Callout>

## Emitting a curve (`xark-curve`)

`xark-curve` is for writing gadgets: each curve is one macro call with its constants. If you want
signature verification, use the signature crates instead. The emitted code refers to
`xark_bignum::…` and `xark::…`, so the crate that calls a macro must depend on both:

```toml
[dependencies]
xark = "0.4"
xark-bignum = "0.4"
xark-curve = "0.4"
```

From `xark-ed25519`'s `src/lib.rs`:

```rust
xark_curve::edwards! {
    base   = "57896044618658097711785492504343953926634992332820282019728792003956564819949",
    scalar = "7237005577332262213973186563042994240857116359379907606001950938285454250989",
    d      = "37095705934669439343138083508754565189542113879843219016388785533085940283555",
}
```

| Macro | What it emits |
| --- | --- |
| `weierstrass!` | A short-Weierstrass curve gadget: `Fp`, `Fq`, `Point`, `enforce_on_curve`, incomplete affine `ec_add_incomplete` / `ec_double_incomplete`, and Strauss–Shamir `double_scalar_mul_incomplete` (`u1·G + u2·Q`) |
| `edwards!` | A twisted-Edwards (`a = −1`) curve gadget: `Fp`, `Fq`, `Point`, `enforce_on_curve`, complete `ec_add` / `ec_double`, `identity`, `scalar_mul` and `double_scalar_mul` |
| `curve_host_inputs!` | The host side both share: `Point` from `x ‖ y` bytes (or SEC1 with `0x04`), and `order()` / `reduce_scalar()`. Needs a host-only `num-bigint` dependency |

`weierstrass!` takes the base and scalar moduli, `a` (`0` or `-3`), `b`, four generator points
and an offset correction; see the `affine` modules of `xark-secp256k1` and `xark-secp256r1`. Field
elements are 3 limbs of 86 bits; an optional leading `bits = N` picks another limb width.

- The Weierstrass addition is incomplete: inputs must be canonical and not hit `P = ±Q`. Check
  points from outside with `enforce_on_curve` first.
- The Edwards addition is complete (no exceptional cases) when `d` is a non-square, as it is for
  Ed25519.

## Recursion

Grumpkin exists here for a reason: it is the half of the BN254↔Grumpkin cycle that is *native* in
a BN254 circuit, and that is what makes in-circuit folding verification practical. What is built
today — IPA accumulator verification, Nova folding steps, a 2-step IVC, the host-side prover, and
the one capability that still blocks a closed loop — is documented in
[Folding & recursion](/docs/reference/folding-and-recursion).
