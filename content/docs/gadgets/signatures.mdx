---
title: Signatures
description: Verify secp256k1, secp256r1 (P-256), and Ed25519 signatures inside a Groth16 circuit.
---

Signature gadgets let a proof say *"this signature is valid for this public key and this
digest"* — and, if you make them private inputs, without revealing the key or the signature. All
three take the same shape — a public key, a signature, and a digest — and all three verify the
curve algebra in-circuit, so the verifier never trusts an oracle.

The three crates share a design: the **digest is an input**, not something the gadget hashes. If
the statement you want is about a *message*, you either hash it with a
[hash gadget](/docs/gadgets/hashes) inside the same circuit, or make the digest public so the
verifier can recompute it from the message. This separation is deliberate — it lets you combine
any hash with any curve, and it keeps the expensive hash out of the circuit when the digest can be
public.

| Gadget | Curve | Verification cost |
| --- | --- | --- |
| `xark-secp256k1` | secp256k1 (Bitcoin, Ethereum) | 227,168 constraints (`examples/secp256k1_ecdsa`) |
| `xark-secp256r1` | P-256 (WebAuthn passkeys) | 344,969 constraints (`examples/secp256r1_ecdsa`) |
| `xark-ed25519` | Ed25519 (Solana keys) | 396,912 constraints (`examples/ed25519`) |

## secp256k1 ECDSA (`xark-secp256k1`)

```rust
use xark_secp256k1::prelude::*;

#[circuit]
pub fn secp256k1_ecdsa(pubkey: Public<Point>, sig: Public<Signature>, digest: Public<Scalar>) {
    pubkey.verify(sig, digest);
}
```

| Type | Host form (bytes) | In-circuit |
| --- | --- | --- |
| `Point` | `[u8; 64]` = `x ‖ y`, SEC1 **without** the `0x04` tag | 2 field elements per coordinate |
| `Signature` | `[u8; 64]` = `r ‖ s` | `(r, s)` |
| `Scalar` | `[u8; 32]` | 2 field elements |

- **`digest` = `int(hash(msg)) mod n`**, computed by the caller. Make it with the host helper
  `reduce_scalar`: `let digest = reduce_scalar(&Sha256::digest(msg));`.
- The gadget checks that the public key is on the curve, that `r`, `s` and the digest are below
  `n`, and that `r` and `s` are nonzero. A wrong signature makes the circuit unsatisfiable.
- No public key is refused. A valid signature is refused only if its nonce `k` is one of six fixed
  multiples of the private key (`k ≡ μ·q`; the constants `μ` are listed in the source).
- `order()` (host only) is the group order `n`. `affine` is a lower-level incomplete-affine curve
  gadget (`Point`, `ec_add_incomplete`, `ec_double_incomplete`, …), used by `examples/ec_incomplete`.

The example's tests verify real signatures from the `k256` crate.

## secp256r1 / P-256 ECDSA (`xark-secp256r1`)

```rust
use xark_secp256r1::prelude::*;

#[circuit]
pub fn secp256r1_ecdsa(pubkey: Public<Point>, sig: Public<Signature>, digest: Public<Scalar>) {
    pubkey.verify(sig, digest);
}
```

The same input types, host forms and checks as secp256k1: the public key is checked on-curve,
`r`, `s` and the digest below `n`, `r` and `s` nonzero. The differences:

- `ecdsa_verify(q, r, s, e)` is the same check with the signature passed as two scalars.
- A valid signature is refused only if its nonce `k` equals `±q`, the private key or its negation.

P-256 is the curve WebAuthn passkeys sign with by default, which makes it the usual choice for
"prove I own this Web2 identity" circuits. The example's tests verify real signatures from the
`p256` crate.

## Ed25519 / EdDSA (`xark-ed25519`)

```rust
use xark_ed25519::prelude::*;

#[circuit]
pub fn ed25519(pubkey: Public<PointL>, sig: Public<Signature>, digest: Public<Scalar>) {
    pubkey.verify(sig, digest);
}
```

| Type | Host form (bytes) | Notes |
| --- | --- | --- |
| `PointL` | `[u8; 32]` | the **compressed** Ed25519 public key `A` |
| `Signature` | `[u8; 64]` | compressed `R (32)` ‖ **big-endian** `S (32)` |
| `Scalar` | `[u8; 32]` big-endian | the challenge `k = SHA-512(R ‖ A ‖ M) mod L` |

The circuit checks the cofactored equation `[8]·([S]·B − [k]·A − R) = O`, with `A` and `R`
canonical and on the curve, and `S < L`. The host helpers build the inputs from an
`ed25519-dalek` signature:

```rust
use xark_ed25519::{challenge, scalar_le_to_be};

let pubkey = sk.verifying_key().to_bytes();
let raw = sk.sign(MSG).to_bytes(); // R(32) ‖ S(32, little-endian)
let mut sig = [0u8; 64];
sig[..32].copy_from_slice(&raw[..32]); // compressed R
sig[32..].copy_from_slice(&scalar_le_to_be(&raw[32..].try_into().unwrap())); // S big-endian

let r: [u8; 32] = sig[..32].try_into().unwrap();
let k = challenge(&r, &pubkey, MSG);
ed25519(pubkey, sig, k).unwrap();
```

| Helper | Does |
| --- | --- |
| `challenge(r, a, msg)` | host: `k = SHA-512(R ‖ A ‖ M) mod L`, big-endian |
| `scalar_le_to_be(le)` | host: turn a standard little-endian `S` into the big-endian form `Signature` takes |
| `point_be`, `base_be`, `base_mul_be` | host: decompress a point; the base point `B`; `[k]·B` |
| `base()`, `mul_base(k_bits)` | in circuit: the base point and fixed-base scalar multiplication |

<Callout type="error" title="The challenge hash is your job">
The SHA-512 challenge is **not** computed in the circuit: the prover supplies `k`, and
`PointL::verify` proves the EdDSA equation for the `k` it's handed. If `k` is public, as above, the
verifier can recompute it from `R`, `A` and the message to tie the proof to that message. If your
statement is "this signature is valid for message `M`" and `k` is private, you must bind `k` to `M`
yourself; otherwise the proof is only about *some* challenge.
</Callout>

## The pattern they share

Each example verifies a signature against a public digest, which proves possession of a valid
signature over *whatever* digest was supplied. To make it a statement about a private message,
compute the digest from the message inside the same circuit with a
[hash gadget](/docs/gadgets/hashes) — for ECDSA, `int(hash(msg)) mod n` — and pass that to
`verify`. Every hash and every signature gadget composes this way, at the sum of their costs.

<Callout type="info" title="What is (and isn't) proven">
Each signature gadget's building blocks — the non-native multiplications, range checks, on-curve
checks, the fused double-and-add steps, and the fake-GLV scalar relations — are proven sound in
Lean 4 over the rows they emit. How the steps are chained across the scalar-multiplication loop is
covered by tests, not by a whole-loop proof. See
[Formal proofs & audit status](/docs/trust/formal-proofs-and-audit).
</Callout>
