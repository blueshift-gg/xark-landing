---
title: Proving in the browser
description: Generate and verify Groth16 proofs client-side with @blueshift-gg/xark — no server, no round trip.
---

The `@blueshift-gg/xark` package bundles the xark prover as WebAssembly, so a browser (or Node, or
an edge runtime) can solve a witness and produce a Groth16 proof **entirely in memory**. Only the
circuit and keys need to be fetched; the witness never leaves the client.

This page is the untyped API. For most apps, a [generated TypeScript client](/docs/guides/typescript-clients)
is the easier path: it wraps this package with your circuit's own types.

<Callout title="Prerequisites">
You need the files `xark build` and `xark setup` produce, served as static files:

```sh
xark build my-circuit   # → target/xark/<name>/circuit.xbc
xark setup my-circuit   # → target/xark/<name>/{pk.bin, vk.bin}
```

`circuit.xbc` is self-contained — it carries both the witness solver and the constraints the
proving key is keyed to — so it is the only circuit file you ship.
</Callout>

## Install and prove

```sh
npm install @blueshift-gg/xark@0.4
```

```js
import init, { prove, verify } from "@blueshift-gg/xark";

await init();

const [circuit, pk, vk] = await Promise.all([
  fetch("/circuit/circuit.xbc").then((r) => r.arrayBuffer()),
  fetch("/circuit/pk.bin").then((r) => r.arrayBuffer()),
  fetch("/circuit/vk.bin").then((r) => r.arrayBuffer()),
]);

const { proof, publicInputs } = prove(circuit, pk, { secret: "3", result: "27" });

verify(vk, proof, publicInputs); // true
```

On **Node 20+** there is no `init()` step:

```js
import { readFileSync } from "node:fs";
import { prove, verify } from "@blueshift-gg/xark";

const xbc = readFileSync("examples/cube/target/xark/cube/circuit.xbc");
const pk = readFileSync("examples/cube/target/xark/cube/pk.bin");
const vk = readFileSync("examples/cube/target/xark/cube/vk.bin");

const { proof, publicInputs } = prove(xbc, pk, { secret: "3", result: "27" });
console.log(verify(vk, proof, publicInputs)); // true
```

Every binary argument accepts a `Uint8Array` **or** an `ArrayBuffer`, so `response.arrayBuffer()`
and a Node `Buffer` can be passed straight through.

## Inputs

`inputs` gives every input a value: keys are the circuit's input names, and values nest to mirror
the input's shape.

```js
prove(xbc, pk, {
  id: { dob: 19940312, net_worth: 2400000n }, // field names as in Rust
  path: ["12", "0x0d"],                       // an array: element i → path[i]
  ok: true,                                   // booleans are 1 / 0
});
```

Scalars may be decimal strings, `0x`-hex strings, safe-integer numbers, or bigints. A field value
must already be a field element: a negative or larger value is rejected rather than reduced, and a
number outside JavaScript's safe-integer range is rejected rather than rounded.

For values in their natural forms (a date, a country, a hash's 32 bytes, a base58 address, a key), encode them first
with the circuit's `schema.json`, exactly as `xark prove --inputs` reads them:
`prove(xbc, pk, encodeInputs(schema, JSON.stringify(inputs)))`.

## API

| Function | Does |
| --- | --- |
| `prove(circuitXbc, pkBytes, inputs, sources?)` | Solve the witness and produce a proof; returns `{ proof, publicInputs, numPublicInputs }` |
| `verify(vkBytes, proofBytes, publicInputsBytes)` | `true` if valid, `false` if well-formed but not verifying; throws on malformed input |
| `preload(circuitXbc, pkBytes, sources?)` / `prove_preloaded(inputs)` | Parse the circuit and decode the key once, then prove many times |
| `new ProvingSession(circuitXbc, pkBytes, sources?)` | What `preload` caches, as an object; several can be loaded at once |
| `decode_public_inputs(publicInputsBytes)` | The public inputs as decimal strings, in proof order |
| `solanaProof(proofBytes)` | The proof as an exported Solana verifier reads it (256 bytes) |
| `encodeInputs(schema, inputs)` | Natural-form inputs (JSON text) → the object `prove` takes |
| `circuitDigest(circuitXbc)` / `sha256Hex(bytes)` | The circuit digest `xark build` prints / a key's hash, for pinning |
| `poseidon2(inputs)` | `xark_poseidon2::hash` of field elements (decimal or `0x`-hex strings), as a decimal string |
| `poseidon2Commit(inputs)` / `poseidon2Nullifier(inputs)` | `xark_poseidon2::commit` / `nullifier`: a note's commitment and its nullifier, as decimal strings |

- A `ProvingSession` has the Poseidon2 functions too, as `commit` and `nullifier`.
- `prove` checks the proof against the key's verifying key before returning it: an unsatisfiable
  witness is an error, never a proof.
- Pass `sources` (the `sources.json` `xark build` writes beside `circuit.xbc`) and a failing input
  is reported as the statement that fails, e.g.
  `` the inputs fail the check at src/lib.rs:77:20: `id.nationality.require_one_of(allowed);` ``.
- `proof` and `publicInputs` are the same bytes as the host's `proof.bin` / `public_inputs.bin`.
  `verify` takes a proof in either form: compressed (128 bytes, as `prove` returns it) or onchain
  (256 bytes).

## Large circuits

Every API proves with a streaming prover: rows, witness and proving key are processed a window at a
time, so neither the constraint system nor the decoded key is ever held whole (Ed25519 verification
proves in about 0.5–0.9 GB). `@blueshift-gg/xark/stream` adds proving while the key downloads:

```js
import * as xark from "@blueshift-gg/xark";
import { proveFromStream } from "@blueshift-gg/xark/stream";

const { proof, publicInputs } = await proveFromStream(
  xark, circuit, fetch("/circuit/pk.bin"), inputs,
  { onProgress: (bytes) => bar.update(bytes) },
);
```

The witness and the quotient polynomial are computed before the first key byte is needed, so
proving overlaps the download. If `xark setup` made a `minimized` key (its `metadata.json` says
`r1cs_form`), it also wrote `r1cs.stream`: pass it as the `r1cs` option.

For threads, `createPool` from `@blueshift-gg/xark/pool` runs the FFT and multi-scalar
multiplications across workers. It needs a cross-origin isolated page, and the proving call must run
in a Web Worker; without isolation `parallelSupported()` is false and the same prover runs on one
thread.

## Where it runs

Anywhere with Web Crypto: browsers, Node 20+, Cloudflare Workers, Vercel Edge, and Deno. Prover
randomness comes from the platform CSPRNG (`crypto.getRandomValues`).

<Callout type="warn" title="Experimental, and the keys still have to be trustworthy">
Browser proving changes *where* the proof is made, not the trust model: a key whose setup
randomness someone kept can forge proofs, in the browser too. Use a key from a
[trusted setup](/docs/trust/trusted-setup) you can stand behind, and treat xark as unaudited
([audit status](/docs/trust/formal-proofs-and-audit)).
</Callout>
