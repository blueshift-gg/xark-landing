title: Serialization & artifacts
description: The files xark writes, and the two encodings — native and onchain.
---

xark writes proofs and keys in two encodings, for two audiences. Knowing which is which saves you a
lot of "why doesn't this verify" confusion.

- **Native (`.bin`)** — Arkworks canonical serialization (`Compress::Yes`, validated on read):
  byte-for-byte what `ark-groth16` 0.6 produces for `VerifyingKey<Bn254>` and `Proof<Bn254>`. This
  is what `xark verify` and `@blueshift-gg/xark`'s `verify` read off-chain.
- **Onchain (`.solana.bin`)** — every field element 32 bytes **little-endian**, points
  uncompressed, G2 as `(c0, c1)`, and a proof as `−A ‖ B ‖ C` (256 bytes). This is what Solana's
  `alt_bn128` syscalls consume; `xark export` writes it, and a TypeScript client's
  `proof.toBytes()` is a proof in it. See [How verification works](/docs/guides/how-verification-works).

`xark verify --proof`, `@blueshift-gg/xark`'s `verify` and a client verifier take a proof in either
form, telling them apart by length (128 bytes compressed, 256 onchain).

## Artifacts

| File | Written by | Contents |
| --- | --- | --- |
| `circuit.xbc` | `xark build` | the circuit, as DAG-compact bytecode — what every later command loads |
| `schema.json` | `xark build` | the circuit's inputs: names, types, public or private, and the public inputs in proof order |
| `sources.json` | `xark build` | which source statement each constraint came from |
| `digest` | `xark build` | the circuit digest `xark build` prints |
| `circuit.json`, `r1cs.json` | `xark build --emit-json` | human-readable views, for debugging; nothing reads them back |
| `profile.json`, `profile.html` | `xark profile` | each constraint's source line, function chain and kind |
| `pk.bin` / `vk.bin` | `xark setup` | a short header + `ProvingKey<Bn254>` / `VerifyingKey<Bn254>` |
| `metadata.json` | `xark setup`, `xark ceremony finalize` | how the key was made, and the circuit it was made for |
| `inputs.example.json` | `xark setup` | every input in its natural form, to fill in for `xark prove` |
| `r1cs.stream` | `xark setup` (a `minimized` key) | the keyed rows, so `xark prove` skips the minimize |
| `pk.decoded.bin` | `xark prove --cache` | the proving key with uncompressed points |
| `proving_key.bin` / `verifying_key.bin` | `xark ceremony` | the same as `pk.bin` / `vk.bin`, from the ceremony |
| `proof.bin` | `xark prove`, `@blueshift-gg/xark`'s `prove` | `Proof<Bn254>` |
| `public_inputs.bin` | `xark prove`, `@blueshift-gg/xark`'s `prove` | an 8-byte little-endian count, then each value as 32 bytes little-endian |
| `verifying_key.solana.bin` | `xark export` | the verifying key, onchain layout |
| `proof.solana.bin` | `xark export` | 256 bytes, `−A ‖ B ‖ C` |
| `public_inputs.solana.bin` | `xark export` | N × 32 bytes, little-endian |
| `instruction_data.bin` | `xark export` | `proof ‖ public_inputs`, onchain layout |

A proving key's header (14 bytes) states whether its points are compressed (the default) or
uncompressed (`xark setup --uncompressed`), and its QAP domain size. A key with a smooth domain
(`3·2^k` or `9·2^k` points, the default without a `.ptau`) can be proved against only by xark's
provers.

Public inputs are in exactly the order the circuit declares its public parameters. The verifier
consumes this order verbatim.

## The circuit artifact

`circuit.xbc` is **not** a flat list of constraints. A signature circuit is hundreds of thousands
of constraints built from a handful of routines — a field multiply, a point add or double — run
thousands of times. So xark stores each repeated piece once as a template, every other occurrence
as a small call record, and rolls long periodic runs; setup and proving expand it on demand. The
expanded circuit is exactly the flat one.

| Circuit | Constraints | `circuit.xbc` |
| --- | ---: | ---: |
| `ed25519` | 396,912 | 6.2 MB |
| `secp256k1_ecdsa` | 227,168 | 4.5 MB |
| `keccak256` | 89,375 | 404 KB |

## metadata.json

`metadata.json` records the circuit a key was made for — `circuit_hash` (the SHA-256 of that
build's `circuit.xbc`), the circuit `digest`, the constraint and public-input counts — and how the
key was made: `setup_mode`, `production_safe`, the deterministic seed if one was used, and for a
`.ptau` setup its `ptau_source` and a `phase2_seed_hash`. It also records the R1CS form, the domain
size, and the verifying key's SHA-256. The setup modes are covered under
[The trusted setup](/docs/trust/trusted-setup).

`xark prove`, `xark verify` and `xark export` read it to refuse a key made for another build of the
circuit, and `xark export` to record how the key was made in the generated crate.

<Callout title="A convenience check, not tamper-proof">
`metadata.json` is a plain JSON file next to the keys — nothing signs it or binds it into
`pk.bin` / `vk.bin`, so anyone who can edit the files can rewrite it. xark reads it to stop your own
slip-ups (e.g. proving circuit B with keys made for circuit A); it is **not** a security boundary.
</Callout>
