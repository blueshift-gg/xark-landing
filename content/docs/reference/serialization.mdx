title: Serialization & artifacts
description: The files xark writes, and the two encodings — native and on-chain.
---

xark writes proofs and keys in two encodings, for two audiences. Knowing which is which saves you a
lot of "why doesn't this verify" confusion.

- **Native (`.bin`)** — Arkworks canonical serialization (`Compress::Yes`, validated on read),
  byte-for-byte what `ark-groth16` 0.6 produces. This is what `xark verify` reads off-chain, and it
  is the authoritative form.
- **On-chain (`.solana.bin`)** — a 32-byte **little-endian**, uncompressed wire format that Solana's
  `alt_bn128` syscalls consume directly. Different byte order, different compression — see
  [How verification works](/docs/guides/how-verification-works).
- **JSON** — snarkjs-compatible, coordinates as decimal strings. See
  [snarkjs interop](/docs/reference/snarkjs).

## Artifacts

| File | Encoding | Produced by | Contents |
| --- | --- | --- | --- |
| `pk.bin` | native | `setup` | `ProvingKey<Bn254>` |
| `vk.bin` | native | `setup` | `VerifyingKey<Bn254>` |
| `proof.bin` | native | `prove` | `Proof<Bn254>` |
| `public_inputs.bin` | native | `prove` | the N public scalars |
| `metadata.json` | JSON | `setup` | circuit hash, `setup_mode`, `production_safe` |
| `snarkjs-*.json` | JSON | `setup`/`prove` | vk / proof / public, decimal strings |
| `verifying_key.solana.bin` | on-chain LE | `export` | VK, little-endian |
| `proof.solana.bin` | on-chain LE | `export` | 256 B, `−A ‖ B ‖ C` |
| `public_inputs.solana.bin` | on-chain LE | `export` | N × 32 B, little-endian |
| `instruction_data.bin` | on-chain LE | `export` | `proof ‖ public_inputs` (what you submit) |

## metadata.json and circuit hash

`circuit_hash` is the **SHA-256 of the circuit's `r1cs.json`**, so it binds the field, the variable
table (which fixes the number, identity, and order of the public inputs), and every constraint
(coefficients and variable indices). If the constraint system changes, the hash changes — which is
how xark detects that a proof and a verifying key belong to different circuits.

`metadata.json` carries that hash alongside key provenance: `protocol`, `curve`, `backend_version`,
`num_public_inputs`, `num_constraints`, and how the keys were made (`setup_mode`, `production_safe`,
and — for production keys — `ptau_source` and a `phase2_seed_hash`). The `setup_mode` /
`production_safe` values are covered under [The trusted setup](/docs/trust/trusted-setup); `export`
refuses to emit a verifier for a non-`production_safe` key unless you pass `--allow-insecure`.

<Callout title="A convenience check, not tamper-proof">
`metadata.json` is a plain JSON file next to the keys — nothing signs it or binds it into
`pk.bin` / `vk.bin`, so anyone who can edit the files can rewrite it. `export` / `prove` read it to
stop your own slip-ups (e.g. proving circuit B with keys made for circuit A); it is **not** a
security boundary.
</Callout>
