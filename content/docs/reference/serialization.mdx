xark writes proofs and keys in two encodings, for two audiences. Knowing which is which saves you a
lot of "why doesn't this verify" confusion.

- **Native (`.bin`)** — Arkworks canonical serialization (`Compress::Yes`, validated on read),
  byte-for-byte what `ark-groth16` 0.6 produces. This is what `xark verify` reads off-chain, and it
  is the authoritative form.
- **On-chain (`.solana.bin`)** — a 32-byte **little-endian**, uncompressed wire format that Solana's
  `alt_bn128` syscalls consume directly. Different byte order, different compression — see
  [How verification works](/docs/guides/how-verification-works).
- **JSON** — snarkjs-compatible, coordinates as decimal strings. See
  [snarkjs interop](/docs/reference/snarkjs).

## Artifacts

A normal `xark build` writes **one** circuit file: `circuit.xbc`. The JSON siblings are opt-in via
`--emit-json`, because serializing them dominates build time (multi-GB on heavy circuits such as
ed25519) and nothing at prove / check / setup time reads them.

| File | Encoding | Produced by | Contents |
| --- | --- | --- | --- |
| `circuit.xbc` | XBC bytecode | `build` | the DAG-compact circuit — the **only** circuit file a normal build writes, and what `prove` / `check` / `setup` load |
| `circuit.json` | JSON | `build --emit-json` | the human-readable primitive / witness program |
| `r1cs.json` | JSON | `build --emit-json` | the flat R1CS (variables + constraints); pretty-printed at ≤ 1M constraints, compact above |
| `graph.dot` | DOT | `build --emit-json` | debug graph of the R1CS; written only at ≤ 1M constraints |
| `profile.json` | JSON | `profile` | per-constraint source / function / kind attribution |
| `r1cs.min.wcz` | binary | `setup --cache` / `prove --cache` | minimized R1CS cache, so a later prove skips the minimize + validate |
| `pk.bin` | native | `setup` | `ProvingKey<Bn254>` |
| `vk.bin` | native | `setup` | `VerifyingKey<Bn254>` |
| `proof.bin` | native | `prove` | `Proof<Bn254>` |
| `public_inputs.bin` | native | `prove` | the N public scalars |
| `metadata.json` | JSON | `setup` | circuit fingerprint, `setup_mode`, `production_safe` |
| `snarkjs-*.json` | JSON | `setup`/`prove` | vk / proof / public, decimal strings |
| `verifying_key.solana.bin` | on-chain LE | `export` | VK, little-endian |
| `proof.solana.bin` | on-chain LE | `export` | 256 B, `−A ‖ B ‖ C` |
| `public_inputs.solana.bin` | on-chain LE | `export` | N × 32 B, little-endian |
| `instruction_data.bin` | on-chain LE | `export` | `proof ‖ public_inputs` (what you submit) |

## The circuit artifact and the JIT prover

`circuit.xbc` is **not** a flat list of constraints. xark treats a circuit's functions as reusable
functions and stores the circuit as a **DAG-compact bytecode** — each distinct function body once,
plus small `(function, base, plugs)` call records — then expands it on demand at setup/prove time.
This is the "JIT prover" model, and it is purely a packaging decision: the expanded circuit is
byte-identical to the flat lowering, and a build-time gate (`XARK_VERIFY`, on for every test build)
decodes the artifact with an independent decoder and asserts equality, aborting on any divergence.

The practical effect is on artifact size on disk, not on proof cost:

| Circuit | Flat | DAG-compact |
| --- | --- | --- |
| ed25519 scalar mult | ~99 MB | ~1.1 MB |
| secp256k1 ECDSA | 33 MB | 2.4 MB |
| Keccak | 2.7 MB | 0.8 MB |

Alongside the bytecode, xark runs a **linear-variable-elimination** pass on the R1CS — Gaussian
elimination that substitutes away every internal variable defined by a linear constraint, to a
fixpoint. It is satisfiability-preserving in both directions, so it changes the circuit's size (and
therefore the proving-key and FFT-domain cost) without changing what is proven. `--cache` persists
the result as `r1cs.min.wcz` so a later `xark prove` reloads it instead of re-deriving it.

`xark inspect <crate>` reports the variable / constraint / public-input counts, and
`xark profile <crate>` attributes each constraint to its source line, function chain, and kind.

## metadata.json and circuit hash

`circuit_hash` is the **SHA-256 of the circuit artifact xark loaded** — the `circuit.xbc` bytes by
default, or the `r1cs.json` text when one is supplied via `--r1cs` (or is all that exists). Either
way it binds the field, the variable table (which fixes the number, identity, and order of the
public inputs), and every constraint (coefficients and variable indices). If the constraint system
changes, the hash changes — which is how xark detects that a proof and a verifying key belong to
different circuits.

`metadata.json` carries that hash alongside key provenance: `protocol`, `curve`, `backend_version`,
`num_public_inputs`, `num_constraints`, and how the keys were made (`setup_mode`, `production_safe`,
and — for production keys — `ptau_source` and a `phase2_seed_hash`). The `setup_mode` /
`production_safe` values are covered under [The trusted setup](/docs/trust/trusted-setup); `export`
refuses to emit a verifier for a non-`production_safe` key unless you pass `--allow-insecure`.

<Callout title="A convenience check, not tamper-proof">
`metadata.json` is a plain JSON file next to the keys — nothing signs it or binds it into
`pk.bin` / `vk.bin`, so anyone who can edit the files can rewrite it. `export` / `prove` read it to
stop your own slip-ups (e.g. proving circuit B with keys made for circuit A); it is **not** a
security boundary.
</Callout>
