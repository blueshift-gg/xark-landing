`xark` builds, tests, proves and verifies zero-knowledge circuits written in Rust, and generates
their Solana verifiers and TypeScript clients. It installs from crates.io and needs stable Rust
1.89 or newer:

```sh
cargo install xark-cli
```

Each command takes the circuit crate's directory, the current one by default, and infers every
path from the crate's `target/xark/<name>/`, where `<name>` is the crate's package name. Most
commands also accept that output directory itself. Flags below override an inferred path.

At a [project](/docs/guides/projects)'s root, `xark build`, `xark test` and `xark check` act on the
whole project, and a command that takes one circuit uses the project's only one (with several,
name it: `xark prove circuits/claim`). A project's keys are in `keys/<name>/` and its generated
clients in `clients/<name>/`.
`xark <command> --help` lists every option; `xark` alone prints the path from a new circuit to an
onchain proof.

## `xark doctor`

Check the toolchain: `cargo`, `rustc` 1.89+, `rustup`, the `wasm32-unknown-unknown` target, the
`xark` that `cargo test` and `rust-analyzer` will run, `cargo build-sbf` and `node`. The last two
are required in a project with programs (`xark build` and `xark test` use them), optional
elsewhere. Exits non-zero when a required check fails.

## `xark init [name]`

Start a project (alias `xark new`): a `xark.toml`, a Cargo workspace, and a starter circuit in
`circuits/<name>/`. With no name, initializes the current directory; the name may be a path, and
the project, its circuit and the circuit's `#[circuit]` function are named after its last
component.

```sh
xark init my-circuit
```

Writes `xark.toml`, `Cargo.toml` (the workspace), `.gitignore`, `rust-analyzer.toml`,
`.vscode/settings.json`, `.github/workflows/ci.yml` (`xark build --check`, then `xark test`), and
the circuit crate: `Cargo.toml` (depending on `xark` at the CLI's own minor version) and
`src/lib.rs` (a square-root circuit and two tests). A `.gitignore`, workflow or editor setting
already there is kept. Refuses a directory that already has a `Cargo.toml`.

## `xark add circuit <name>`

Add a circuit to the project: the crate `xark init` makes, in `circuits/<name>/`. A name can't end
in `-program` or `-verifier`: those are the crates `xark add` makes beside it.

## `xark add program <name> [--circuit <circuit>]`

Add a Pinocchio program that verifies a circuit's proofs (the one named `<name>`, or `--circuit`):
`programs/<name>/` (the crate `<name>-program`: `lib.rs`, `errors.rs`, `instructions/verify.rs`),
and a LiteSVM test, `tests/<name>.test.ts`, that proves with the circuit's TypeScript client and
sends the proof to it. Builds the circuit's keys and clients first if they're missing, and writes
`package.json`, `tsconfig.json` and `vitest.config.ts` if the project has none.

## `xark build [crate-dir]`

Compile a circuit crate — Rust → wasm32 → xark-IR → R1CS — into `target/xark/<name>/`, and print
its size and circuit digest. At a project's root, build every circuit, make its keys if there are
none, generate its clients (`clients/<name>/{rust,ts}`), then build the programs with
`cargo build-sbf`, failing when a function's stack frame passes SBF's 4 KiB.

```sh
xark build examples/cube
```

- `--out <DIR>` — output directory (default `<crate>/target/xark/<name>/`).
- `--field <F>` — `bn254` (the default, and the field keys and proofs use), or a prime modulus in
  decimal, to count constraints over another field.
- `--emit-json` — also write `circuit.json` and `r1cs.json`, human-readable views for debugging.
  Nothing reads them back, and they are multi-GB on large circuits, so they're off by default.
- `--check` — at a project's root, for CI: build everything, but fail if the committed clients
  aren't what the source generates, or a key is missing or for an older circuit. Writes nothing.

## `xark check [crate-dir]`

Validate a circuit crate and report Rust the circuit can't express as compiler diagnostics, with
source spans. This is what `rust-analyzer` runs on save in a project `xark init` made: at the root,
`cargo check` over the whole workspace, then each circuit's validation.

```sh
xark check examples/cube --message-format=json
xark check examples/cube --inputs '{"secret": 3, "result": 27}'
```

- `--message-format json` — the JSON diagnostics stream `cargo check` emits. In this mode `check`
  first runs the `cargo check --all-targets` it replaces, so errors in tests and other host-only
  code still show.
- `--inputs <JSON|FILE>` — also build the circuit, solve the witness from these inputs, and report
  any derived variable the constraints fail to pin. Takes every input, as `xark prove` does.
- `--out <DIR>` — output directory for the build `--inputs` runs.

To wire it into an existing crate, point `rust-analyzer` at it:

```toml
# rust-analyzer.toml
[check]
overrideCommand = ["xark", "check", ".", "--message-format=json"]
```

## `xark test [crate-dir] [cargo test args…]`

Build the circuit, then run the crate's tests with `cargo test --release`. Arguments after the
crate directory go to `cargo test` verbatim: a test-name filter, cargo flags, and after `--` the
test binary's own. At a project's root, test every circuit, then build the project and run the
programs' and verifier crates' Rust tests and `npm test`.

```sh
xark test examples/cube
xark test examples/cube -- --nocapture
```

## `xark inspect [crate-dir]`

Print the circuit's size — variable counts by visibility, the constraint count, and the
**public-input count and order** — building it first if it's missing or stale.

```sh
xark inspect examples/cube [--json]
```

- `--json` — machine-readable output.

## `xark profile [crate-dir]`

Build the circuit and attribute each constraint to its source line, function chain and kind, then
print a sorted drill-down. Writes `profile.json`.

- `--html` — also write `profile.html`: the breakdown, with the circuit's source shaded by what
  each line costs.
- `--json` — print the aggregated drill-down as JSON.
- `--out <DIR>`, `--field <F>` — as for `xark build`.

## `xark setup [path]`

Make the Groth16 proving and verifying keys.

```sh
# a single-party setup from OS randomness
xark setup examples/cube

# phase 2 on a Powers-of-Tau transcript
xark setup examples/cube --ptau-file powersOfTau.ptau
```

With no `--ptau-file`, setup looks for a `.ptau` in `target/xark/<name>/`, `target/xark/`, the
crate root, or a `ptau/` directory in any of them; with none found, it makes the key from OS
randomness. Either way it prints how the key was made and the verifying key's SHA-256.

- `--ptau-file <PATH>` — phase 2 on a Powers-of-Tau (`.ptau`) transcript.
- `--phase2-seed <HEX>` — 32-byte seed for the phase-2 `(γ, δ)` derivation (from OS randomness when
  omitted). Only its hash is recorded; discard the seed.
- `--deterministic-rng <SEED>` — derive the key from a seed, for reproducible test fixtures
  **only**: anyone who knows the seed can forge proofs. Skips an auto-detected `.ptau`, and is
  refused with `--ptau-file`.
- `--out <DIR>` — where to write the keys (default `keys/<name>/` in a project, where they're
  committed, otherwise `target/xark/<name>/`). A proving key over 50 MB gets a note to commit it
  with Git LFS.
- `--r1cs-form <auto|reduced|minimized>` — which form of the constraints to key. `auto` (the
  default) picks `reduced` at or above 2²⁰ constraints, and `minimized` below that only where it
  saves enough to matter.
- `--domain <auto|smooth|radix2>` — the QAP evaluation domain. `smooth` (the default without a
  `.ptau`) picks the smallest of `2^k`, `3·2^k` or `9·2^k` points, up to 44% smaller for a circuit
  just past a power of two; only xark's provers can prove against such a key. `radix2` is what
  every Groth16 prover expects, and what a `.ptau` setup uses.
- `--uncompressed` — write the proving key with uncompressed points: twice the size on disk, but
  `xark prove` skips decompressing them.

In a project, the `circuit.xbc` the key was made from is kept beside it: a key proves only with that
build, so `xark prove` and the clients prove with it. It also writes `inputs.example.json` to
`target/xark/<name>/`: every input in its natural form, to
fill in for `xark prove`. A
`minimized` key also gets `r1cs.stream`, which `xark prove` streams. See
[The trusted setup](/docs/trust/trusted-setup) for which setup to use when.

## `xark ceremony`

Run a multi-party phase-2 setup, so the keys don't depend on any single party.

```sh
xark ceremony init examples/cube --ptau-file final.ptau --out ceremony/
xark ceremony contribute --ceremony-dir ceremony/ --label alice
xark ceremony verify examples/cube --ceremony-dir ceremony/ --ptau-file final.ptau
xark ceremony finalize --ceremony-dir ceremony/ --ptau-file final.ptau
```

- `init [path]` — start a ceremony from a `.ptau` and the circuit's `circuit.xbc`. Requires
  `--ptau-file` and `--out`; `--phase2-seed <HEX>` reproduces byte-identical initial keys, and
  `--force` replaces a ceremony already in `--out`.
- `contribute` — apply one contributor's randomness in place. Requires `--ceremony-dir`;
  `--label <NAME>` names the contributor in the attestation (default `anonymous`).
- `verify [path]` — check the contribution chain, and that the keys are the circuit's (recomputed
  from the `.ptau`) with only δ changed. Requires `--ceremony-dir` and `--ptau-file`.
- `finalize [path]` — run `verify`, then mark the chain finished and write the final
  `metadata.json`. Takes the same arguments as `verify`.

The ceremony's keys are `proving_key.bin` and `verifying_key.bin` in the ceremony directory. Full
walkthrough in [The trusted setup](/docs/trust/trusted-setup).

## `xark prove [path]`

Solve the witness from `--inputs` and make a Groth16 proof, checked against the verifying key
before it's written. Builds the circuit first if it's missing or older than its sources, and, when
there is no proving key, makes one from OS randomness as `xark setup` would without a `.ptau`.

```sh
xark prove examples/cube --inputs '{"secret": 3, "result": 27}'
xark prove examples/cube --inputs inputs.json
```

- `--inputs <JSON|FILE>` — every input, as inline JSON `{"name": value, …}` or a file (a JSON
  object, or `name = value` lines with `#` comments). Names may be as declared (`net_worth`) or
  camelCase (`netWorth`, as a TypeScript client has them). Inputs that fail a check are reported as
  the source line that fails.
- `--proving-key <PATH>` — default `target/xark/<name>/pk.bin`.
- `--out <DIR>` — where to write the proof (default `target/xark/<name>/`).
- `--cache` — also write the caches that make later proofs against this key faster:
  `pk.decoded.bin` (the proving key with uncompressed points, twice its size) and, for a
  `minimized` key without one, `r1cs.stream`. Existing caches are always used.
- `--low-memory` — keep one domain-sized vector in memory during the quotient step, parking the
  others in a temp file, to prove the largest circuits on small machines.
- `--deterministic-rng <SEED>` — reproducible proof randomness for test fixtures **only**. Proof
  randomness blinds the witness, so a reproducible proof leaks witness information across proofs.

Writes `proof.bin` and `public_inputs.bin`, and prints how long the witness solve and the prove
took, under the proof's summary:

```text
✅ Proof produced and self-checked (1 public input(s)).
   solved in 0.00s, proved in 0.00s
```

## `xark verify [path]`

Check a proof against the verifying key and its public inputs. Prints `✅ Proof verified`, or exits
non-zero.

```sh
xark verify examples/cube
```

- `--inputs <JSON|FILE>` — the public inputs, as for `xark prove`; when omitted, they are read from
  `public_inputs.bin`.
- `--verifying-key`, `--proof`, `--public-inputs` — override the inferred paths. `--proof` takes a
  proof in either form: compressed (`proof.bin`) or onchain (256 bytes).

## `xark export [path]`

Generate the Solana verifier crate, with the verifying key embedded.

```sh
xark export examples/cube
```

`xark build` runs it for every circuit of a project.

- `--out <DIR>` — the generated crate's root. Default `clients/<name>/rust/` at a project's root
  (or `<crate>/clients/rust/` for a crate outside a project). An existing `Cargo.toml` or
  `src/lib.rs` that `xark export` didn't write is never replaced.
- `--crate-name <NAME>` — the generated crate's package name (default `<name>-verifier`).
- `--verifying-key`, `--proof`, `--public-inputs` — override the inferred paths. The proof is
  bundled as the crate's self-test; without one (or with one for another key) the crate has no
  self-test. A sample the crate already bundles is kept while it still verifies, so a rebuild
  doesn't change the crate.

Any key exports. The crate's `SETUP` constant, its README, and `export`'s output record how the key
was made: `seeded`, `single-party`, `ceremony` (two or more contributors), or `unknown`.

## `xark client [path]`

Generate a typed TypeScript client from the build's `schema.json`, building the circuit first if
needed. No setup or proof is required.

`xark build` runs it for every circuit of a project.

- `--out`, `-o <PATH>` — an output file, or a directory to write `<circuit>.ts` in (default
  `clients/<name>/ts/<circuit>.ts` at a project's root).
- `--lang ts` — the client language; TypeScript is the one there is.
- `--no-functions` — skip the Rust client functions (`#[input]` on an `impl`), for a crate whose
  host code doesn't build for wasm.

See [TypeScript clients](/docs/guides/typescript-clients).

## `xark clean`

Remove all xark build output: every `target/xark/`, `target/xark-wasm/` and `target/xark-client/`
under the current directory.

## `xark completions <shell>`

Print a shell completion script for `bash`, `elvish`, `fish`, `powershell` or `zsh`.
