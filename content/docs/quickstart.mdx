---
title: Quickstart
description: From a Rust circuit to a proof verified by a Solana program, in five steps.
---

In this quickstart you'll write a circuit that proves you know a square root of a public number,
test it, prove it, and verify the proof in a Solana program.

<Callout title="Prerequisites">
Stable Rust **1.89 or newer** ([rustup](https://rustup.rs)). `xark build` adds the
`wasm32-unknown-unknown` target with `rustup` the first time it runs. To build the Solana program
at the end, you'll also want the [Anza CLI](https://docs.anza.xyz/cli/install) (`cargo-build-sbf`)
and [Node](https://nodejs.org).
</Callout>

<Steps>

<Step>
### Install the CLI

```sh
cargo install xark-cli
xark doctor
```

`xark doctor` checks your toolchain and tells you how to fix anything that's missing.
</Step>

<Step>
### Start a project

```sh
xark init my-circuit && cd my-circuit
```

This makes a project: a `xark.toml`, one Cargo workspace, and a circuit crate in
`circuits/my-circuit/` that depends on `xark = "0.4"`, set up so `rust-analyzer` shows circuit
errors inline. Open `circuits/my-circuit/src/lib.rs`:

```rust
use xark::prelude::*;

#[circuit]
pub fn my_circuit(secret: Private<Field>, result: Public<Field>) {
    // prove knowledge of a square root: secret * secret == result
    require_eq(secret * secret, result);
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn accepts_valid() {
        my_circuit(2, 4).unwrap(); // 2 * 2 == 4
    }

    #[test]
    fn rejects_invalid() {
        assert!(my_circuit(3, 4).is_err()); // 3 * 3 != 4
    }
}
```

`secret` is private: only the prover knows it. `result` is public: the verifier sees it.
`require_eq` is a constraint — the proof exists only if it holds. The tests call the circuit
like a function, with plain integers for its `Field` inputs.
</Step>

<Step>
### Test it

At the project's root, `xark test` builds the circuit, then runs its tests:

```console
$ xark test
xark building circuit `my-circuit`
xark 2 vars, 1 constraints, 0 witness-gen ops
xark circuit digest 75e3ce529473dfaa2f89a85a0d588228
...
test tests::accepts_valid ... ok
test tests::rejects_invalid ... ok
```

The whole circuit is one constraint. The digest is a fingerprint of that constraint system: the
same for every build of this circuit, whichever Rust compiled it.
</Step>

<Step>
### Prove

```console
$ xark prove --inputs '{"secret": 3, "result": 9}'
...
✅ Proof produced and self-checked (1 public input(s)).
   solved in 0.00s, proved in 0.00s
```

The first proof also makes the proving and verifying keys, in `keys/my-circuit/`. Now try inputs
that don't satisfy the circuit — xark shows you the line that fails:

```console
$ xark prove --inputs '{"secret": 3, "result": 10}'
error: witness does not satisfy the circuit

  circuits/my-circuit/src/lib.rs:6:16  require_eq(secret * secret, result);
```
</Step>

<Step>
### Verify it on Solana

`xark add program` generates the circuit's verifier crate and TypeScript client, then writes a
Pinocchio program that verifies the circuit's proofs, and a LiteSVM test that proves with the
client and sends the proof to it. `xark build` builds whatever is out of date, here only the
program; `xark test` runs every test:

```console
$ xark add program my-circuit
...
xark added program `my-circuit-program` in .../programs/my-circuit, verifying `my-circuit`
$ xark build
xark circuit `circuits/my-circuit` is unchanged since the last build
xark verifier crate `my-circuit-verifier` at .../clients/my-circuit/rust is unchanged
xark TypeScript client for `my_circuit` at .../clients/my-circuit/ts/my_circuit.ts is unchanged
xark building the programs (cargo build-sbf)
$ npm install && xark test
...
 Test Files  1 passed (1)
```

Commit everything `xark build` writes, `keys/` included: the generated clients embed the
verifying key.
</Step>

</Steps>

## The program's side

The program depends on `clients/my-circuit/rust/`, the verifier crate `xark build` generates
(`my-circuit-verifier`). It reads the 256-byte proof from the instruction data and supplies the
public inputs it requires itself, from its own state, by name:

```rust
let Some(proof) = instruction_data.first_chunk::<256>() else {
    return Err(ProgramError::InvalidInstructionData);
};
let proof = my_circuit_verifier::Proof::from_le_bytes(proof);
let inputs = my_circuit_verifier::PublicInputs {
    result: /* from your program's state, 32 bytes little-endian */,
};
if !my_circuit_verifier::verify(&proof, inputs) {
    return Err(ProgramError::InvalidArgument);
}
```

`PublicInputs` has the circuit's public inputs by name, and `verify` packs them as the circuit
does. When the circuit changes, `xark build` regenerates the crate; your program's code stays put.
For the byte layout and the syscalls behind that one call, see
[How verification works](/docs/guides/how-verification-works), and for the project's layout,
[Projects](/docs/guides/projects).

<Callout type="warn" title="Before you deploy">
The key `xark prove` made is a single-party setup: sound unless whoever ran it kept its
randomness. xark never writes that randomness down, but a key that holds value should come from a
setup no single party has to be trusted for. See [The trusted setup](/docs/trust/trusted-setup).
</Callout>
