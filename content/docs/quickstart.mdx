---
title: Quickstart
description: From a Rust circuit to a proof and a Solana verifier crate, in five steps.
---

In this quickstart you'll write a circuit that proves you know a square root of a public number,
test it, prove it, and generate the crate a Solana program uses to verify the proof.

<Callout title="Prerequisites">
Stable Rust **1.89 or newer** ([rustup](https://rustup.rs)). `xark build` adds the
`wasm32-unknown-unknown` target with `rustup` the first time it runs. To build the Solana program
that uses the verifier at the end, you'll also want the [Anza CLI](https://docs.anza.xyz/cli/install)
(`cargo-build-sbf`).
</Callout>

<Steps>

<Step>
### Install the CLI

```sh
cargo install xark-cli
xark doctor
```

`xark doctor` checks your toolchain and tells you how to fix anything that's missing.
</Step>

<Step>
### Create a circuit

```sh
xark init my-circuit
```

This writes a circuit crate that depends on `xark = "0.3"`, set up so `rust-analyzer` shows
circuit errors inline. Open `my-circuit/src/lib.rs`:

```rust
use xark::prelude::*;

#[circuit]
pub fn my_circuit(secret: Private<Field>, result: Public<Field>) {
    // prove knowledge of a square root: secret * secret == result
    require_eq(secret * secret, result);
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn accepts_valid() {
        my_circuit(2, 4).unwrap(); // 2 * 2 == 4
    }

    #[test]
    fn rejects_invalid() {
        assert!(my_circuit(3, 4).is_err()); // 3 * 3 != 4
    }
}
```

`secret` is private: only the prover knows it. `result` is public: the verifier sees it.
`require_eq` is a constraint — the proof exists only if it holds. The tests call the circuit
like a function, with plain integers for its `Field` inputs.
</Step>

<Step>
### Test it

`xark test` builds the circuit, then runs the crate's tests:

```console
$ xark test my-circuit
xark building circuit `my-circuit`
xark 2 vars, 1 constraints, 0 witness-gen ops
xark circuit digest 75e3ce529473dfaa2f89a85a0d588228
...
test tests::accepts_valid ... ok
test tests::rejects_invalid ... ok
```

The whole circuit is one constraint. The digest is a fingerprint of that constraint system: the
same for every build of this circuit, whichever Rust compiled it.
</Step>

<Step>
### Prove

```console
$ xark prove my-circuit --inputs '{"secret": 3, "result": 9}'
...
✅ Proof produced and self-checked (1 public input(s)).
```

The first proof also makes the proving and verifying keys. Now try inputs that don't satisfy the
circuit — xark shows you the line that fails:

```console
$ xark prove my-circuit --inputs '{"secret": 3, "result": 10}'
error: witness does not satisfy the circuit

  src/lib.rs:6:16  require_eq(secret * secret, result);
```
</Step>

<Step>
### Verify, then export the Solana verifier

```console
$ xark verify my-circuit
✅ Proof verified

$ xark export my-circuit
...
✅ On-chain verifier crate ready (verifying key embedded).
```

`export` writes `my-circuit/my-circuit-verifier/`: a crate with the verifying key embedded,
and the proof you just made bundled as its self-test.
</Step>

</Steps>

## Then, on Solana

Your program depends on the generated crate. It reads the 256-byte proof from the instruction
data and supplies the public inputs it requires itself, from its own state:

```rust
let Some(proof) = instruction_data.first_chunk::<256>() else {
    return Err(ProgramError::InvalidInstructionData);
};
let proof = my_circuit_verifier::Proof::from_le_bytes(proof);
let public_inputs: [[u8; 32]; 1] = [/* from your program's state */];
if !my_circuit_verifier::verify(&proof, &public_inputs) {
    return Err(ProgramError::InvalidArgument);
}
```

Re-run `xark export` whenever the circuit changes; the generated crate is the only thing that
updates. For the byte layout and the syscalls behind that one call, see
[How verification works](/docs/guides/how-verification-works).

<Callout type="warn" title="Before you deploy">
The key `xark prove` made is a single-party setup: sound unless whoever ran it kept its
randomness. xark never writes that randomness down, but a key that holds value should come from a
setup no single party has to be trusted for. See [The trusted setup](/docs/trust/trusted-setup).
</Callout>
