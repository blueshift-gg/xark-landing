---
title: "06 · Shielded transfer"
description: Merkle trees and range proofs together. Private payments of any amount, Zcash-style. Notes, a key hierarchy, a JoinSplit circuit, an SPL token pool and a relayer.
---

In this tutorial you'll build a shielded pool for an SPL token. Anyone can deposit tokens into it,
pay anyone else any amount inside it, and withdraw. Onchain, an observer sees tokens go in and
come out, but never who paid whom, or how much.

This is where the story comes together: **Merkle trees and range proofs**.
[04 · Shielded pool](/docs/tutorials/04-shielded-pool) used [03](/docs/tutorials/03-token-claim)'s
Merkle tree and [02](/docs/tutorials/02-zkyc)'s commitments to move fixed amounts from a deposit to
a withdrawal, and [05 · Anonymous voting](/docs/tutorials/05-anonymous-voting) made each nullifier
from a secret key and what it's scoped to. Here notes carry any amount, and the circuit has to
prove that what goes in equals what comes out without revealing either. That only works because every amount is a
[range-checked](/docs/learn-zk/range-proofs) `u64`, the idea [01](/docs/tutorials/01-over-9000)
started with. On top of 04, this one adds what a payment system needs:

- **notes**: hidden amounts, each range-checked, each owned by an address;
- a **key hierarchy**: one secret key, with a viewing key and any number of addresses derived from
  it;
- **JoinSplit**: one circuit that spends two notes and creates two, as long as the values balance;
- **SPL tokens**: a token vault the program pays out of;
- **relayers**: someone else submits your transaction, for a fee, so your wallet never appears
  beside it.

By the end, an end-to-end test will run this story against your program: Alice deposits 150
tokens, pays Bob 100 privately and keeps 45 as change, with 5 to a relayer. Bob, who holds no SOL
at all, withdraws 95 through the relayer, who takes another 5.

## One circuit for everything

Every operation is one `transact`: spend two notes, create two notes, and balance the difference
against two **public** amounts, `vpub_in` (value entering the pool) and `vpub_out` (value
leaving it), plus the relayer's `fee`:

```text
spent (2 notes) + vpub_in  ==  created (2 notes) + vpub_out + fee
```

- A **deposit** has `vpub_in > 0`. Its spends are dummies.
- A **transfer** has `vpub_in = vpub_out = 0`. No tokens move onchain, except a fee.
- A **withdrawal** has `vpub_out > 0`.

A slot you don't need takes a **dummy**: a note worth 0 that isn't checked against the tree. So
every transaction has the same shape: one circuit, one instruction, the same public inputs.

<Step>
### Append two leaves at once

04's deposit appends one leaf with `Path::append`. A transaction here creates two notes, and the
program always appends them as a pair, at an even slot. A pair at an even slot is one leaf of the
tree one level up, the tree of pairs, whose empty leaf is `hash2(ZERO_LEAF, ZERO_LEAF)`. So
appending a pair is `xark-merkle`'s `merkle_append` again, on the path's upper 19 levels. Append to
`circuits/pool/src/lib.rs`:

```rust title="circuits/pool/src/lib.rs"
impl Path {
    /// In a circuit: this path's slot is even and it and the slot after it are empty
    /// in the tree rooted at `old_root`, and the result is that root with `pair`
    /// written in them. The pair is one leaf of the tree of pairs, the subtrees of
    /// height 1, whose empty leaf is `hash2(ZERO_LEAF, ZERO_LEAF)`: `merkle_append`
    /// on the path's upper 19 levels.
    pub fn append_pair(&self, old_root: Field, pair: [Field; 2]) -> Field {
        let bits = bits(self.index);
        require_eq(bits[0], Field::from(0u64));
        let mut siblings = [Field::from(0u64); H - 1];
        let mut up = [Field::from(0u64); H - 1];
        let mut i = 0;
        while i < H - 1 {
            siblings[i] = self.siblings[i + 1];
            up[i] = bits[i + 1];
            i += 1;
        }
        let empty = Field::from(ZERO_LEAF);
        merkle_append(
            old_root,
            xark_poseidon2::hash2(empty, empty),
            xark_poseidon2::hash2(pair[0], pair[1]),
            siblings,
            up,
        )
    }
}
```

The index's lowest bit must be 0, so the pair starts at an even slot. The other 19 bits and the
path's siblings above the pair are a path in the tree of pairs, and `merkle_append` proves, with
that one path, that the pair's slot was empty under `old_root` and what the root is with the
pair's node in it. That replaces a separate check of the old root: hashing the empty pair up the
path must give `old_root`, which pins the path to the tree's true nodes, as in 04's deposit.
</Step>

<Step>
### Write the circuit

Replace `circuits/shielded_transact/src/lib.rs` with the circuit's types. Each `#[input]` type is
an input the client takes as it is, and each `#[input] impl` is Rust the client can call:

```rust title="circuits/shielded_transact/src/lib.rs"
use pool::Path;
use xark::prelude::*;
use xark_hash::Hash;
use xark_poseidon2::{commit, hash};

// The keys' tags, on top of `hash`'s length tag: no two kinds of key collide, and
// `hash` is a domain apart from `commit`'s and `nullifier`'s.
const NULLIFIER_KEY: u64 = 1;
const VIEWING_KEY: u64 = 2;
const ADDRESS: u64 = 3;

/// A holder's spending key: their other keys and every address derive from it.
#[input]
pub struct Key {
    pub secret: Field,
}

#[input]
impl Key {
    /// What nullifiers are made with.
    pub fn nullifier_key(&self) -> Field {
        hash([self.secret, Field::from(NULLIFIER_KEY)])
    }

    /// What addresses are made from: whoever has it recognizes the holder's addresses.
    pub fn viewing_key(&self) -> Field {
        hash([self.secret, Field::from(VIEWING_KEY)])
    }

    /// Address number `diversifier`: as many as the holder likes, unlinkable to
    /// each other without the viewing key.
    pub fn address(&self, diversifier: Field) -> Field {
        hash([self.viewing_key(), diversifier, Field::from(ADDRESS)])
    }
}

/// `value` of the pool's token, owned by `owner` (a `Key::address`). `rho` and
/// `rseed` are the sender's randomness: they make every note unique and hidden.
#[input]
pub struct Note {
    pub value: u64,
    pub owner: Field,
    pub rho: Field,
    pub rseed: Field,
}

#[input]
impl Note {
    /// The leaf the note is in the tree as, in the pool of `asset` (its mint).
    pub fn commitment(&self, asset: Address) -> Field {
        let [hi, lo] = asset.to_fields();
        let [value, owner, rho, rseed] = self.to_fields();
        commit([value, owner, rho, rseed, hi, lo])
    }

    /// What spending the note at `position` reveals: only `key`'s holder can make
    /// it, and it's the same every time, so the program refuses a second spend.
    pub fn nullifier(&self, key: Key, asset: Address, position: u32) -> Field {
        nullifier(key.nullifier_key(), self.commitment(asset), position)
    }
}

fn nullifier(nullifier_key: Field, commitment: Field, position: u32) -> Field {
    xark_poseidon2::nullifier([nullifier_key, commitment, Field::from(position)])
}

/// A note to spend, at `path`, owned by the spender's address `diversifier`.
/// A dummy (`real: false`) is worth 0 and its path isn't checked.
#[input]
pub struct Spend {
    pub note: Note,
    pub diversifier: Field,
    pub path: Path,
    pub real: bool,
}

/// The value moving in and out of the pool: `vpub_in` from the user's token
/// account, `vpub_out` to `recipient`, and `fee` to `relayer`, the token account
/// of whoever submits the transaction.
#[input]
pub struct Flow {
    pub vpub_in: u64,
    pub vpub_out: u64,
    pub fee: u64,
    pub recipient: Address,
    pub relayer: Address,
}

/// The public inputs, in the order the program assembles them.
#[input]
pub struct Transaction {
    pub root: Field,
    pub asset: Address,
    pub nullifiers: [Field; 2],
    pub commitments: [Field; 2],
    pub old_root: Field,
    pub new_root: Field,
    pub index: u32,
    pub flow: Flow,
    pub memos: [Hash; 2],
}

#[input]
impl Transaction {
    /// `key` spends `spends` and creates `outputs`, appended at `tip` (the next
    /// free leaf's path) in the pool of `asset`.
    #[cfg(not(xark))]
    pub fn of(
        key: Key,
        spends: [Spend; 2],
        outputs: [Note; 2],
        tip: Path,
        asset: Address,
        flow: Flow,
        memos: [Hash; 2],
    ) -> Transaction {
        let commitments = outputs.map(|o| o.commitment(asset));
        Transaction {
            root: tip.tree_root(),
            asset,
            nullifiers: spends.map(|s| s.note.nullifier(key, asset, s.path.index)),
            commitments,
            old_root: tip.tree_root(),
            new_root: tip.next(commitments[0]).next(commitments[1]).tree_root(),
            index: tip.index,
            flow,
            memos,
        }
    }
}
```

The key hierarchy is three hashes, each with a tag of its own. Spending needs `secret`. `viewing_key` is enough to recognize
your addresses, so you could hand it to an auditor without giving them your funds. `address` makes
as many addresses as you like from one key, and nobody can tell two of them belong together.

The mint, the recipient and the relayer are Solana addresses, so they're xark's `Address`: two
field elements, its 16-byte halves, which `to_fields` hands the hash. A note is a `commit` to its
value, its owner, two random fields and the token's mint, so notes in different pools never
collide. Its nullifier is a `nullifier` of the owner's nullifier key, as a voter's was in
[05](/docs/tutorials/05-anonymous-voting), the note's commitment and its position in the tree: only
the owner can compute it, and it doesn't reveal which commitment it came from. `commit` and
`nullifier` are `xark-poseidon2`'s sponge, each in a domain of its own, so a commitment, a
nullifier, a key and a tree node can never stand in for one another. See
[Hashes](/docs/gadgets/hashes).

`Transaction::of` builds the whole public statement from these helpers, for the client: the new
root is the wallet's own `next`, twice. It's `#[cfg(not(xark))]`: host code only, never part of the
circuit.

Now append the circuit itself:

```rust title="circuits/shielded_transact/src/lib.rs"
#[circuit]
pub fn shielded_transact(
    key: Private<Key>,
    spends: Private<[Spend; 2]>,
    outputs: Private<[Note; 2]>,
    tip: Private<Path>,
    tx: Public<Transaction>,
) {
    let nullifier_key = key.nullifier_key();

    // Spend: each note is the spender's and burns the nullifier revealed. A real
    // one is in the tree; a dummy is worth nothing.
    let mut value_in = Field::from(tx.flow.vpub_in);
    for (spend, revealed) in spends.into_iter().zip(tx.nullifiers) {
        require_eq(spend.note.owner, key.address(spend.diversifier));
        let commitment = spend.note.commitment(tx.asset);
        if spend.real {
            require_eq(spend.path.root(commitment), tx.root);
        } else {
            require(spend.note.value == 0);
        }
        require_eq(
            nullifier(nullifier_key, commitment, spend.path.index),
            revealed,
        );
        value_in += Field::from(spend.note.value);
    }

    // Create: the outputs are the commitments revealed.
    let mut value_out = Field::from(tx.flow.vpub_out) + Field::from(tx.flow.fee);
    for (output, revealed) in outputs.into_iter().zip(tx.commitments) {
        require_eq(output.commitment(tx.asset), revealed);
        value_out += Field::from(output.value);
    }
    // Every value is a range-checked `u64`, so these sums can't wrap the field.
    require_eq(value_in, value_out);

    // Append the pair at `index`, an even slot whose pair was empty. As in 04's
    // deposit, the old root pins `tip` to the tree's true nodes.
    require(tip.index == tx.index);
    require_eq(tip.append_pair(tx.old_root, tx.commitments), tx.new_root);

    // Where the value, the fee and the memos go are the ones the proof was made for.
    bind(tx.flow.recipient);
    bind(tx.flow.relayer);
    for memo in tx.memos {
        bind(memo);
    }
}
```

In one proof, this checks that each spent note belongs to the spender, is in the tree (unless it's
a dummy), and burns the nullifier revealed; that the outputs are the commitments revealed; and that
value balances. As in 04, the chain never hashes: `append_pair` proves the two new notes take the
tree from `old_root` to `new_root`, so the program only stores roots.

<Callout title="Why every amount is range-checked">
`require_eq(value_in, value_out)` is an equation in the field, where arithmetic wraps at `p`. On
its own, it would accept a transaction that spends two dummies and brings nothing in, whose
outputs are a note worth 1,000 and a note worth `p − 1,000`: the outputs sum to `p`, which is 0, the same as the inputs. The second note acts
as −1,000, and 1,000 tokens appear from nowhere.

What stops it is the type. `value`, `vpub_in`, `vpub_out` and `fee` are all `u64` inputs, so xark
[range-checks](/docs/learn-zk/range-proofs) each to 64 bits as it's read, and `p − 1,000` has no
64-bit decomposition. Each side then sums at most four values below 2^64, far below `p`, so the
field equation is the integer equation: value is conserved, exactly. No comparison is needed; the
range checks alone make the sum mean what it says.
</Callout>

The recipient, the relayer and the memos' hashes are used in no other constraint, so `bind`, as in
04's withdraw circuit, ties each to the proof. Without it, a relayer could swap them freely.

### Test the circuit

Append the tests to `circuits/shielded_transact/src/lib.rs`:

```rust title="circuits/shielded_transact/src/lib.rs"
#[cfg(test)]
mod tests {
    use super::*;
    use xark::prover::ProveError;

    fn asset() -> Address {
        [7; 32].into()
    }

    fn note(key: Key, value: u64, rho: u64) -> Note {
        Note {
            value,
            owner: key.address(Field::from(1u64)),
            rho: Field::from(rho),
            rseed: Field::from(rho + 1),
        }
    }

    fn spend(note: Note, path: Path) -> Spend {
        Spend {
            note,
            diversifier: Field::from(1u64),
            path,
            real: true,
        }
    }

    fn dummy(key: Key, rho: u64) -> Spend {
        Spend {
            real: false,
            ..spend(note(key, 0, rho), Path::first())
        }
    }

    /// Run the circuit on `spends` → `outputs`, the tree's next free leaf at `tip`,
    /// with `(vpub_in, vpub_out, fee)`.
    fn transact(
        key: Key,
        spends: [Spend; 2],
        outputs: [Note; 2],
        tip: Path,
        vpub: (u64, u64, u64),
    ) -> Result<(), ProveError> {
        let flow = Flow {
            vpub_in: vpub.0,
            vpub_out: vpub.1,
            fee: vpub.2,
            recipient: [9; 32].into(),
            relayer: [8; 32].into(),
        };
        let memos = [[1; 32].into(), [2; 32].into()];
        // `Transaction::of` appends the pair as the wallet does (`next`, twice), so
        // a proof that holds is the circuit's `append_pair` agreeing with it.
        let tx = Transaction::of(key, spends, outputs, tip, asset(), flow, memos);
        shielded_transact(key, spends, outputs, tip, tx)
    }

    #[test]
    fn deposit_then_pay_privately() {
        let alice = Key { secret: Field::from(42u64) };
        let bob = Key { secret: Field::from(99u64) };
        let dummies = [dummy(alice, 100), dummy(alice, 101)];

        // Alice deposits 150: nothing spent, 150 in. Not 151.
        let mine = note(alice, 150, 1);
        let deposit = [mine, note(alice, 0, 2)];
        transact(alice, dummies, deposit, Path::first(), (150, 0, 0)).unwrap();
        let greedy = [note(alice, 151, 1), deposit[1]];
        assert!(transact(alice, dummies, greedy, Path::first(), (150, 0, 0)).is_err());

        // Her note's path changed when the deposit's second output landed beside it.
        let a = asset();
        let after_mine = Path::first().next(mine.commitment(a));
        let path = Path::first().update(after_mine, deposit[1].commitment(a));
        let tip = after_mine.next(deposit[1].commitment(a));

        // She pays Bob 100 and keeps 45; a relayer takes 5. Nothing moves publicly
        // but the fee.
        let spends = [spend(mine, path), dummy(alice, 102)];
        let pay = [note(bob, 100, 3), note(alice, 45, 4)];
        transact(alice, spends, pay, tip, (0, 0, 5)).unwrap();

        // Bob can't spend Alice's note, and nobody can pay out more than they spend.
        assert!(transact(bob, [spend(mine, path), dummy(bob, 102)], pay, tip, (0, 0, 5)).is_err());
        assert!(transact(alice, spends, [note(bob, 101, 3), pay[1]], tip, (0, 0, 5)).is_err());
        // Outputs land in pairs, at an even index.
        assert!(transact(alice, spends, pay, tip.next(Field::from(5u64)), (0, 0, 5)).is_err());
    }
}
```

The test is a small wallet: it tracks Alice's note's path with `Path::next` and `Path::update`
from the `pool` crate, as 04's wallet did. Every proof that holds is the circuit's `append_pair`
agreeing with the wallet's `next`, twice; the last line moves the tip to an odd slot, where
`append_pair` refuses. Run it:

```console

running 1 test

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 7.22s
```

### Add the program

The program is Pinocchio, as in 01 to 04, and has two instructions:

- `initialize` creates a pool for one SPL mint, at a PDA seeded by the mint, and its token vault.
- `transact` checks the proof against the pool's state and the transaction's accounts, burns the
  two nullifiers, moves the public amounts in or out of the vault, stores the new root and logs
  the two memos.

didn't make a proof first, so the crate has no bundled self-test this time. The end-to-end test is
the check.

checks. See [Call the circuit's Rust from TypeScript](/docs/guides/typescript-clients#call-the-circuits-rust-from-typescript).
</Step>

### Lay out the accounts

The program owns two kinds of account, each at a PDA, and creates a third:

| PDA | Seeds | Owner | Size |
|---|---|---|--:|
| `pool` | `["pool", mint]` | this program | 554 |
| `vault` | `["vault", mint]` | the token program: a token account owned by `pool` | 165 |
| `nullifier` | `["nullifier", mint, nf]` | this program | 0 |

A nullifier holds no data: that its account exists is what counts. Create
`programs/shielded-transfer/src/state.rs`:

```rust title="programs/shielded-transfer/src/state.rs"
use pinocchio::{AccountView, Address, ProgramResult, error::ProgramError};
use pinocchio_token::state::Account as TokenAccount;

use crate::helpers::{token_account, writable};

pub const TREE_HEIGHT: u32 = 20;
pub const ROOT_HISTORY_SIZE: usize = 16;
pub const POOL_SEED: &[u8] = b"pool";
pub const VAULT_SEED: &[u8] = b"vault";
pub const NULLIFIER_SEED: &[u8] = b"nullifier";

// The empty tree's root, little-endian: `Path.first().treeRoot()`. Fixed here so
// a pool can't be seeded with another tree.
pub const EMPTY_ROOT: [u8; 32] = [
    251, 142, 67, 247, 199, 111, 241, 124, 245, 96, 180, 214, 179, 51, 248, 149, 20, 177, 173, 83,
    193, 126, 124, 38, 168, 0, 139, 11, 55, 225, 46, 3,
];

/// A pool's account, 554 bytes: `mint`, `next_index` and `current_root_index`
/// (u32 LE), a ring of the 16 most recent roots, then the pool's and the vault's
/// bumps.
#[repr(C)]
pub struct Pool {
    pub mint: [u8; 32],
    next_index: [u8; 4],
    current_root_index: [u8; 4],
    roots: [[u8; 32]; ROOT_HISTORY_SIZE],
    pub bump: u8,
    pub vault_bump: u8,
}

const _: () = assert!(Pool::LEN == 554);

impl Pool {
    pub const LEN: usize = size_of::<Self>();

    /// The pool `data` holds, if it is a pool's size.
    pub fn load(data: &[u8]) -> Result<&Self, ProgramError> {
        if data.len() != Self::LEN {
            return Err(ProgramError::InvalidAccountData);
        }
        // SAFETY: `Pool` is all byte arrays (alignment 1, any bit pattern valid),
        // and `data` is exactly its size.
        Ok(unsafe { &*data.as_ptr().cast::<Self>() })
    }

    /// As `load`, to write.
    pub fn load_mut(data: &mut [u8]) -> Result<&mut Self, ProgramError> {
        if data.len() != Self::LEN {
            return Err(ProgramError::InvalidAccountData);
        }
        // SAFETY: as above.
        Ok(unsafe { &mut *data.as_mut_ptr().cast::<Self>() })
    }

    /// Write a new pool into a freshly created account, which is zeroed: the
    /// ring's other slots are empty.
    pub fn init(data: &mut [u8], mint: &[u8; 32], bump: u8, vault_bump: u8) -> ProgramResult {
        let pool = Self::load_mut(data)?;
        pool.mint = *mint;
        pool.roots[0] = EMPTY_ROOT;
        pool.bump = bump;
        pool.vault_bump = vault_bump;
        Ok(())
    }

    pub fn next_index(&self) -> u32 {
        u32::from_le_bytes(self.next_index)
    }

    pub fn current_root(&self) -> &[u8; 32] {
        let i = u32::from_le_bytes(self.current_root_index) as usize % ROOT_HISTORY_SIZE;
        &self.roots[i]
    }

    /// Remember `root` as the newest in the ring, and advance the tree by a pair.
    /// The caller has checked the tree has room.
    pub fn push_root(&mut self, root: &[u8; 32]) {
        let i = (u32::from_le_bytes(self.current_root_index) as usize + 1) % ROOT_HISTORY_SIZE;
        self.current_root_index = (i as u32).to_le_bytes();
        self.roots[i] = *root;
        self.next_index = (self.next_index() + 2).to_le_bytes();
    }

    /// One of the recent roots. The ring's unused slots are zero; no root is.
    pub fn knows_root(&self, root: &[u8; 32]) -> bool {
        root != &[0; 32] && self.roots.contains(root)
    }
}
```

As in 04, every field is a byte array, so the account's data is the struct and `load` reads it in
place. The roots start at offset 40, which is where the test will read the empty root. A pool and a
nullifier are told apart by size, 554 bytes or none.
</Step>

The pool's checks read the pool, so they go with it: the pool itself, and the vault built from the
new helpers. Append to `programs/shielded-transfer/src/state.rs`:

```rust title="programs/shielded-transfer/src/state.rs"
impl Pool {
    /// A pool account: writable, owned by this program, a pool's size, at the
    /// address its own mint and stored bump derive.
    pub fn check(account: &AccountView) -> ProgramResult {
        writable(account)?;
        if !account.owned_by(&crate::ID) {
            return Err(ProgramError::InvalidAccountOwner);
        }
        let data = account.try_borrow()?;
        let pool = Self::load(&data)?;
        let address =
            Address::derive_address(&[POOL_SEED, &pool.mint], Some(pool.bump), &crate::ID);
        if account.address() != &address {
            return Err(ProgramError::InvalidSeeds);
        }
        Ok(())
    }

    /// The pool's vault: at the address the pool's mint and stored vault bump
    /// derive, a token account of the pool's mint, owned by the pool.
    pub fn check_vault(&self, vault: &AccountView, pool: &Address) -> ProgramResult {
        let seeds = [VAULT_SEED, &self.mint];
        let address = Address::derive_address(&seeds, Some(self.vault_bump), &crate::ID);
        if vault.address() != &address {
            return Err(ProgramError::InvalidSeeds);
        }
        token_account(vault, &self.mint)?;
        if TokenAccount::from_account_view(vault)?.owner() != pool {
            return Err(ProgramError::IncorrectAuthority);
        }
        Ok(())
    }
}
```

`writable`, `writable_signer`, `system_program`, `is_uninitialized` and `Pool::check` prevent what
they did in 04. The new ones:

- **`token_program`**: the token CPIs call the token program by its address, so a fake couldn't
  be called in its place; the check names a wrong account list first, with `IncorrectProgramId`.
- **`mint`**: `Mint::from_account_view` refuses an account that isn't the token program's or isn't
  a mint's size, so no one can open a pool for a fake mint.
- **`token_account`**: an initialized token account of the pool's mint. The token program would
  refuse a transfer between two mints anyway; checking first fails with `WrongMint` before
  verification spends its compute units.
- **`Pool::check_vault`**: at its PDA, a token account of the pool's mint, owned by the pool.
  Without it, a depositor could name a token account of their own as the vault: the tokens would
  go back to them, and their new note would be backed by nothing.
</Step>

```rust title="programs/shielded-transfer/src/instructions/initialize.rs"
use pinocchio::{
    AccountView, Address, ProgramResult,
    cpi::{Seed, Signer},
    error::ProgramError,
};
use pinocchio_token::{instructions::InitializeAccount3, state::Account as TokenAccount};

use crate::{
    helpers::{is_uninitialized, mint, system_program, token_program, writable, writable_signer},
    state::{POOL_SEED, Pool, VAULT_SEED},
};

/// Accounts: the pool and the vault (the PDAs, not yet created), the mint, the
/// authority (pays the rent), the token program, the system program.
pub struct InitializeAccounts<'a> {
    pub pool: &'a mut AccountView,
    pub vault: &'a mut AccountView,
    pub mint: &'a AccountView,
    pub authority: &'a AccountView,
}

impl<'a> TryFrom<&'a mut [AccountView]> for InitializeAccounts<'a> {
    type Error = ProgramError;

    fn try_from(accounts: &'a mut [AccountView]) -> Result<Self, Self::Error> {
        let [pool, vault, mint_account, authority, token, system, ..] = accounts else {
            return Err(ProgramError::NotEnoughAccountKeys);
        };
        writable_signer(authority)?;
        token_program(token)?;
        system_program(system)?;
        mint(mint_account)?;
        writable(pool)?;
        writable(vault)?;
        Ok(Self {
            pool,
            vault,
            mint: mint_account,
            authority,
        })
    }
}

/// Create the pool for one SPL mint, with the empty tree's root, and its vault.
/// No instruction data.
pub struct Initialize<'a> {
    pub accounts: InitializeAccounts<'a>,
    pub bump: u8,
    pub vault_bump: u8,
}

impl<'a> TryFrom<(&'a [u8], &'a mut [AccountView])> for Initialize<'a> {
    type Error = ProgramError;

    fn try_from((data, accounts): (&'a [u8], &'a mut [AccountView])) -> Result<Self, Self::Error> {
        if !data.is_empty() {
            return Err(ProgramError::InvalidInstructionData);
        }
        let accounts = InitializeAccounts::try_from(accounts)?;
        // One pool and one vault per mint, each at its canonical bump.
        let mint = accounts.mint.address().as_array();
        let (address, bump) = Address::find_program_address(&[POOL_SEED, mint], &crate::ID);
        let (vault_address, vault_bump) =
            Address::find_program_address(&[VAULT_SEED, mint], &crate::ID);
        if accounts.pool.address() != &address || accounts.vault.address() != &vault_address {
            return Err(ProgramError::InvalidSeeds);
        }
        if !is_uninitialized(accounts.pool) || !is_uninitialized(accounts.vault) {
            return Err(ProgramError::AccountAlreadyInitialized);
        }
        Ok(Self {
            accounts,
            bump,
            vault_bump,
        })
    }
}

impl<'a> Initialize<'a> {
    pub const DISCRIMINATOR: &'a u8 = &0;

    pub fn process(&mut self) -> ProgramResult {
        let mint = self.accounts.mint.address().as_array();
        let bump = [self.bump];
        let seeds = [Seed::from(POOL_SEED), Seed::from(mint), Seed::from(&bump)];
        pinocchio_system::create_account_with_minimum_balance_signed(
            self.accounts.pool,
            Pool::LEN,
            &crate::ID,
            self.accounts.authority,
            None,
            &[Signer::from(&seeds)],
        )?;
        Pool::init(
            &mut self.accounts.pool.try_borrow_mut()?,
            mint,
            self.bump,
            self.vault_bump,
        )?;

        // The vault: a token account of `mint` at its PDA, owned by the pool.
        let vault_bump = [self.vault_bump];
        let seeds = [
            Seed::from(VAULT_SEED),
            Seed::from(mint),
            Seed::from(&vault_bump),
        ];
        pinocchio_system::create_account_with_minimum_balance_signed(
            self.accounts.vault,
            TokenAccount::LEN,
            &pinocchio_token::ID,
            self.accounts.authority,
            None,
            &[Signer::from(&seeds)],
        )?;
        InitializeAccount3::new(
            self.accounts.vault,
            self.accounts.mint,
            self.accounts.pool.address(),
        )
        .invoke()
    }
}
```

The pool is 04's: one per mint, created zeroed by `pinocchio-system` with only the first root set.
The vault is 03's: a token account at a PDA, created by the program and initialized with
`InitializeAccount3`, with the pool's PDA as its owner, so only this program, signing with the
pool's seeds, can move its tokens. The checks, and what they prevent:

- **There is no instruction data**, so a malformed instruction is refused before anything reads
  it.
- **The pool and the vault are the mint's PDAs at their canonical bumps**, the ones
  `find_program_address` returns. Another bump would give another valid address, and so a second
  pool for the same mint. The pool stores both bumps, so `Pool::check` and `Pool::check_vault`
  derive the two addresses without searching again.
- **Neither exists yet**, so no one can reinitialize a live pool and wipe its roots.
</Step>

```rust title="programs/shielded-transfer/src/instructions/transact.rs"
/// program.
```

Then its instruction data. A transact's arguments are their bytes in order, then the two memos,
each its length then its bytes, since a memo's size is up to the wallet. Append:

```rust title="programs/shielded-transfer/src/instructions/transact.rs"
/// Data: proof (256) ‖ root (32) ‖ nf[0] ‖ nf[1] ‖ cm_out[0] ‖ cm_out[1] ‖
/// new_root (32 each) ‖ vpub_in ‖ vpub_out ‖ fee (u64 LE each) ‖ memo0 ‖ memo1
/// (each its length as a u32 LE, then its bytes).
pub struct TransactInstructionData<'a> {
    pub proof: &'a [u8; 256],
    pub root: &'a [u8; 32],
    pub nf: [&'a [u8; 32]; 2],
    pub cm_out: [&'a [u8; 32]; 2],
    pub new_root: &'a [u8; 32],
    pub vpub_in: u64,
    pub vpub_out: u64,
    pub fee: u64,
    pub memos: [&'a [u8]; 2],
}

impl<'a> TryFrom<&'a [u8]> for TransactInstructionData<'a> {
    type Error = ProgramError;

    fn try_from(mut data: &'a [u8]) -> Result<Self, Self::Error> {
        let proof = take(&mut data)?;
        let root = take(&mut data)?;
        let nf = [take(&mut data)?, take(&mut data)?];
        let cm_out = [take(&mut data)?, take(&mut data)?];
        let new_root = take(&mut data)?;
        let vpub_in = u64::from_le_bytes(*take(&mut data)?);
        let vpub_out = u64::from_le_bytes(*take(&mut data)?);
        let fee = u64::from_le_bytes(*take(&mut data)?);
        let memos = [memo(&mut data)?, memo(&mut data)?];
        if !data.is_empty() {
            return Err(ProgramError::InvalidInstructionData);
        }
        Ok(Self {
            proof,
            root,
            nf,
            cm_out,
            new_root,
            vpub_in,
            vpub_out,
            fee,
            memos,
        })
    }
}

/// The next `N` bytes of `data`.
fn take<'a, const N: usize>(data: &mut &'a [u8]) -> Result<&'a [u8; N], ProgramError> {
    let (head, rest) = data
        .split_first_chunk()
        .ok_or(ProgramError::InvalidInstructionData)?;
    *data = rest;
    Ok(head)
}

/// A memo: its length as a u32 LE, then that many bytes.
fn memo<'a>(data: &mut &'a [u8]) -> Result<&'a [u8], ProgramError> {
    let len = u32::from_le_bytes(*take(data)?) as usize;
    let (memo, rest) = data
        .split_at_checked(len)
        .ok_or(ProgramError::InvalidInstructionData)?;
    *data = rest;
    Ok(memo)
}
```

Short data, a memo longer than what's left, and trailing bytes all fail with
`InvalidInstructionData`, so a malformed transaction is refused before anything reads it.

```rust title="programs/shielded-transfer/src/instructions/transact.rs"
    type Error = ProgramError;

    fn try_from((data, accounts): (&'a [u8], &'a mut [AccountView])) -> Result<Self, Self::Error> {
        let accounts = TransactAccounts::try_from(accounts)?;
        let data = TransactInstructionData::try_from(data)?;
        let (mint, bump) = {
            let pool = accounts.pool.try_borrow()?;
            let pool = Pool::load(&pool)?;
            (pool.mint, pool.bump)
        };
        // Each nullifier's account: at its canonical PDA, per mint, not yet created.
        let mut nullifier_bumps = [0; 2];
        for (i, nullifier) in accounts.nullifiers.iter().enumerate() {
            let seeds = [NULLIFIER_SEED, &mint, data.nf[i]];
            let (address, bump) = Address::find_program_address(&seeds, &crate::ID);
            if nullifier.address() != &address {
                return Err(ProgramError::InvalidSeeds);
            }
            if !is_uninitialized(nullifier) {
                return Err(ShieldedTransferError::NullifierSpent.into());
            }
            nullifier_bumps[i] = bump;
        }
        Ok(Self {
            accounts,
            data,
            mint,
            bump,
            nullifier_bumps,
        })
    }
}

impl<'a> Transact<'a> {
    pub const DISCRIMINATOR: &'a u8 = &1;

    pub fn process(&mut self) -> ProgramResult {
        use ShieldedTransferError::*;
        let (accounts, data) = (&mut self.accounts, &self.data);
        let index = {
            let pool = accounts.pool.try_borrow()?;
            let pool = Pool::load(&pool)?;
            if u64::from(pool.next_index()) + 2 > 1 << TREE_HEIGHT {
                return Err(TreeFull.into());
            }
            let recipient = accounts.recipient_token;
            if !proves(pool, data, recipient, accounts.relayer_token)? {
                return Err(InvalidProof.into());
            }
            pool.next_index()
        };

        // Spend the notes: create each nullifier's account, empty, paid by the user.
        for (i, nullifier) in accounts.nullifiers.iter_mut().enumerate() {
            let bump = [self.nullifier_bumps[i]];
            let seeds = [
                Seed::from(NULLIFIER_SEED),
                Seed::from(&self.mint),
                Seed::from(data.nf[i]),
                Seed::from(&bump),
            ];
            pinocchio_system::create_account_with_minimum_balance_signed(
                nullifier,
                0,
                &crate::ID,
                accounts.user,
                None,
                &[Signer::from(&seeds)],
            )?;
        }

        // Value entering the pool: user → vault, signed by the user.
        if data.vpub_in > 0 {
            let from = accounts.user_token.ok_or(NoSource)?;
            Transfer::new(from, accounts.vault, accounts.user, data.vpub_in).invoke()?;
        }

        // Value leaving it, signed by the pool PDA: `vpub_out` to the recipient, `fee`
        // to the relayer.
        let bump = [self.bump];
        let seeds = [
            Seed::from(POOL_SEED),
            Seed::from(&self.mint),
            Seed::from(&bump),
        ];
        let payouts = [
            (data.vpub_out, accounts.recipient_token, NoRecipient),
            (data.fee, accounts.relayer_token, NoRelayer),
        ];
        for (amount, to, missing) in payouts {
            if amount > 0 {
                let to = to.ok_or(missing)?;
                Transfer::new(accounts.vault, to, accounts.pool, amount)
                    .invoke_signed(&[Signer::from(&seeds)])?;
            }
        }

        // The chain never hashes the tree: it takes the new root the proof checked.
        Pool::load_mut(&mut accounts.pool.try_borrow_mut()?)?.push_root(data.new_root);
        // What a wallet scans for: each new note's leaf index, commitment and memo.
        for (i, (commitment, memo)) in data.cm_out.iter().zip(data.memos).enumerate() {
            let leaf_index = (index + i as u32).to_le_bytes();
            log_data(&[&leaf_index, *commitment, memo]);
        }
        Ok(())
    }
}
```

Every check runs before anything changes:

- **Each nullifier is at its canonical PDA.** `find_program_address` returns the one bump; another
  would be a second account for the same nullifier, and a second spend of the note. So the program
  finds the bump itself, rather than taking one from the client.
- **Each nullifier is not yet created**, or the note is spent, with `NullifierSpent`. As in 04, it
  may already hold lamports, so no one can block a spend by funding its nullifier's address.
- **The tree has room for two more leaves**, or the transaction fails with `TreeFull`.

Which accounts the payouts go to isn't checked here: the proof binds the recipient and the relayer,
so `verify` checks them. Then the nullifiers are burned, paid for by `user`, and the value moves. A
deposit moves `vpub_in` from the user's token account with a plain `Transfer`, signed by the user. A
withdrawal and a fee move out of the vault with `invoke_signed`, signed by the pool PDA's seeds, as
03's claim pays out. Last, the pool takes the new root the proof checked, and `log_data` publishes
each new note's leaf index, commitment and encrypted memo as `Program data:`, for wallets to scan.
</Step>

<Step>
### Assemble the public inputs

Append `proves`, which fills in the circuit's public `Transaction` and makes the one typed
`verify` call:

```rust title="programs/shielded-transfer/src/instructions/transact.rs"
/// Does the proof verify against the circuit's public `Transaction`, assembled
/// here? It checks `root` against the pool's ring first. In its own stack frame:
/// the inputs and the pairing check's locals don't fit beside `process`'s.
#[inline(never)]
fn proves(
    pool: &Pool,
    data: &TransactInstructionData,
    recipient: Option<&AccountView>,
    relayer: Option<&AccountView>,
) -> Result<bool, ProgramError> {
    if !pool.knows_root(data.root) {
        return Err(ShieldedTransferError::UnknownRoot.into());
    }
    // A left-out recipient or relayer is the program's address.
    let address = |a: Option<&AccountView>| *a.map_or(&crate::ID, |a| a.address()).as_array();
    let inputs = PublicInputs {
        tx: Transaction {
            root: *data.root,
            asset: pool.mint,
            nullifiers: data.nf.map(|nf| *nf),
            commitments: data.cm_out.map(|cm| *cm),
            old_root: *pool.current_root(),
            new_root: *data.new_root,
            index: pool.next_index(),
            flow: Flow {
                vpub_in: data.vpub_in,
                vpub_out: data.vpub_out,
                fee: data.fee,
                recipient: address(recipient),
                relayer: address(relayer),
            },
            memos: data.memos.map(|memo| hash(memo).to_bytes()),
        },
    };
    Ok(verify(&Proof::from_le_bytes(data.proof), inputs))
}
```

The pattern is 04's: the program never parses the proof's claims. It fills in the public inputs
itself, from its own state (the mint, the current root, the next index) and from the transaction
(the nullifiers, the commitments, the amounts, the token accounts and the memos' SHA-256). The
verifier crate's `Transaction` and `Flow` are the circuit's, with the same fields, so a missing or
misnamed one doesn't compile. `verify` turns them into the 19 field elements in the circuit's
order: it splits the mint, the token accounts and the memo hashes into their two halves, and packs
`Flow`'s three amounts into one element, as the circuit's `#[input]` does. A proof made for other
accounts or other memos doesn't verify. See
[Where the public inputs come from](/docs/guides/how-verification-works#where-the-public-inputs-come-from).

The memos stay off-circuit: the program hashes each one and the circuit only binds the hash, so
encryption costs no constraints. `proves` is `#[inline(never)]`, so the 19 inputs and the pairing check's
locals get a stack frame of their own rather than crowding `process`'s: SBF gives each frame 4 KiB.
</Step>

```ts title="tests/shielded-transfer.test.ts"
const pay = (owner: Key, value: bigint): Output => {
  const diversifier = random();

/** What moves publicly, and between which token accounts. */
interface Moves { vpubIn?: bigint; vpubOut?: bigint; fee?: bigint; userToken?: Address; recipient?: Address; relayerToken?: Address }

/**
 * Prove one transaction: `key` spends `spends` and creates `outputs`. `instruction`
 * is what to send; `landed` records the new notes in every wallet once it has.
 */
async function prepare(p: Pool, key: Key, spends: [Spend, Spend], outputs: [Output, Output], moves: Moves = {}) {
  const { vpubIn = 0n, vpubOut = 0n, fee = 0n } = moves;
  const memos = outputs.map(() => crypto.getRandomValues(new Uint8Array(48))); // each note, encrypted to its owner
  const flow = { vpubIn, vpubOut, fee, recipient: moves.recipient ?? program, relayer: moves.relayerToken ?? program };
  const notes = [outputs[0].note, outputs[1].note] as const;
  // The public statement, computed by the circuit's own Rust.
  const tx = Transaction.of(key, spends, notes, p.tip, p.mint, flow, [sha256(memos[0]), sha256(memos[1])]);
  const proof = prover.prove({ key, spends, outputs: notes, tip: p.tip, tx });
  const [n0, n1] = await Promise.all(tx.nullifiers.map((n) => getProgramDerivedAddress({ programAddress: program, seeds: ["nullifier", bytes(p.mint), n.toBytes()] })));
  const optional = (a?: Address) => (a ? writable(a) : readonly(program)); // the program's "none"

  return {
    instruction: (user: KeyPairSigner, accounts: Moves = moves): Instruction => ({
      programAddress: program,
      accounts: [
        writable(p.poolAddress), writable(p.vault), writable(n0[0]), writable(n1[0]), signer(user),
        optional(accounts.userToken), optional(accounts.recipient), optional(accounts.relayerToken),
        readonly(TOKEN_PROGRAM_ADDRESS), readonly(system),
      ],
      data: instructionData(
        TRANSACT, proof.toBytes(), tx.root.toBytes(), ...tx.nullifiers.map((n) => n.toBytes()), ...tx.commitments.map((c) => c.toBytes()),
        tx.newRoot.toBytes(), u64le(vpubIn), u64le(vpubOut), u64le(fee), vec(memos[0]), vec(memos[1]),
      ),
    }),
    landed(): Owned[] {
      const created: Owned[] = [];
      for (const [i, leaf] of tx.commitments.entries()) {
        for (const held of [...p.held, ...created]) held.path = held.path.update(p.tip, leaf);
        created.push({ ...outputs[i], path: p.tip });
        p.tip = p.tip.next(leaf);
      }
      p.held.push(...created);
      return created;
    },
  };
}

/** Prove and send one transaction, signed by `user`; returns the new notes. */
async function transact(p: Pool, user: KeyPairSigner, key: Key, spends: [Spend, Spend], outputs: [Output, Output], moves: Moves = {}) {
  const t = await prepare(p, key, spends, outputs, moves);
  const result = await send(p.svm, user, budget, t.instruction(user));
  console.log(`transact verified onchain in ${result.computeUnitsConsumed()} CU`);
  return t.landed();
}
```

A few things to notice:

- **The wallet never re-implements the circuit.** `Key.address`, `Transaction.of`, `Path.first`,
  `path.update` and `path.next` are the Rust you wrote, run from TypeScript.
- **The account lists are the program's.** `initialize` takes six accounts and `transact` ten, in
  the order the program destructures them, and the data is the discriminator, then the arguments in
  the order `TransactInstructionData` reads them.
- **Solana addresses are @solana/kit's.** `Transaction.of` takes the mint, and `flow` the token
  accounts, as the `Address`es they are; the client splits each into the circuit's two halves.
- **Every note gets a fresh address.** `pay` picks a random diversifier each time, so Bob's notes
  don't share an owner field anyone could link.
- **The memos are stand-ins.** A real wallet encrypts each note's value, `rho` and `rseed` to its
  owner; here they're random bytes. The proof binds their SHA-256 either way, and the program
  recomputes it.
- **An unused token account is the program's address.** The program reads it as none, and the
  proof binds the same address in its place.
- **The mint and the token accounts are written straight into LiteSVM** with `setAccount`, rather
  than created through the token program: a test doesn't need the transactions that make them.
- **The prover proves on a worker pool** from `@blueshift-gg/xark/pool`, which spreads each proof
  over your cores. See [Prove on several threads](/docs/guides/typescript-clients#prove-on-several-threads).

```ts title="tests/shielded-transfer.test.ts"
  expect(balance(p.svm, p.vault)).toBe(145n);

  // 3. Bob withdraws 95 to his token account, 5 to the relayer. Nobody can redirect either.
  const withdrawal = await prepare(p, bob, [spend(toBob), dummy(bob)], [pay(bob, 0n), pay(bob, 0n)], { vpubOut: 95n, fee: 5n, recipient: bobToken, relayerToken });
  const thief = await funded(p.svm);
  const elsewhere = await tokenAccount(p.svm, p.mint, thief.address, 0n);
  await expect(send(p.svm, thief, budget, withdrawal.instruction(thief, { recipient: elsewhere, relayerToken }))).rejects.toThrow(/InvalidProof/);
  await expect(send(p.svm, thief, budget, withdrawal.instruction(thief, { recipient: bobToken, relayerToken: elsewhere }))).rejects.toThrow(/InvalidProof/);
  const result = await send(p.svm, relayer, budget, withdrawal.instruction(relayer));
  console.log(`withdrawal verified onchain in ${result.computeUnitsConsumed()} CU`);
  withdrawal.landed();
  expect(balance(p.svm, bobToken)).toBe(95n);
  expect(balance(p.svm, p.vault)).toBe(45n); // Alice's change, still shielded

  // Bob's note is spent: its nullifier account exists.
  await expect(send(p.svm, relayer, budget, withdrawal.instruction(relayer))).rejects.toThrow(/NullifierSpent/);
});

test("only a note's owner can spend it", async () => {
  const p = await pool();
  const [alice, mallory] = [{ secret: random() }, { secret: random() }];
  const user = await funded(p.svm);
  const token = await tokenAccount(p.svm, p.mint, user.address, 150n);
  const [note] = await transact(p, user, alice, [dummy(alice), dummy(alice)], [pay(alice, 150n), pay(alice, 0n)], { vpubIn: 150n, userToken: token });
  await expect(transact(p, user, mallory, [spend(note), dummy(mallory)], [pay(mallory, 150n), pay(mallory, 0n)])).rejects.toThrow(/key\.address\(spend\.diversifier\)/);
});
```

Look at who signs what. Alice's SOL wallet signs her deposit, because tokens leave her account.
The relayer signs her payment and Bob's withdrawal, so neither Alice nor Bob appears beside them.
The relayer can't cheat for it: the withdrawal's proof names Bob's token account and the relayer's,
so a thief who redirects either one gets `InvalidProof`. A second withdrawal of the same note fails
with `NullifierSpent`, because its nullifier account already exists. And when Mallory tries to
spend Alice's note, the client refuses to prove, naming the circuit line that fails.
</Step>

## What you built

A shielded pool for any SPL token. Alice deposited, paid Bob privately and kept her change; Bob
withdrew without ever holding SOL. Onchain there was a deposit into the vault, a withdrawal
out of it, two fees and three transactions of commitments and nullifiers, with no link between
the deposit and the withdrawal.

The pieces were the ones from earlier tutorials, combined. A note is 02's salted commitment,
carrying a value. A spend is 03's Merkle membership with 04's nullifier, made from a key as 05's was. The vault is 03's. And
01's range proof is what makes it a payment system: every amount is a range-checked `u64`, so the
balance equation that ties the spends to the outputs can't wrap around the field and mint money.
The public inputs let a relayer submit your transaction without being able to change it.

That's the whole arc: range proofs make comparisons and sums mean what they say, commitments hide
values while fixing them, Merkle trees prove membership in a set without naming the member, and
together they make private payments.

This is a teaching version of a deployed system. Before any real use, it would still need:

- real memo encryption (for example x25519 with ChaCha20-Poly1305) and a wallet that
  trial-decrypts memos to find its notes;
- a way to order transactions: each proof binds the current root and append index, so when two
  land at once, the second must be proved again;
- an audit, legal review, and keys from a ceremony.

<Callout type="warn" title="Before you deploy">
The key `xark add program` made is single-party: anyone who kept its randomness could forge proofs
and drain the vault. A pool that holds value needs a key from a multi-party ceremony. See
[The trusted setup](/docs/trust/trusted-setup).
</Callout>

The finished example is
[06-shielded-transfer](https://github.com/blueshift-gg/xark-examples/tree/main/06-shielded-transfer)
in xark-examples. It adds a demo proof bundled as the verifier crate's self-test, host tests that
feed each account check the accounts it exists to refuse, and more refusals in its end-to-end test.
