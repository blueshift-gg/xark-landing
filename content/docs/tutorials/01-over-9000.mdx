---
title: "01 · Over 9000"
description: Your first range proof. Prove a secret number is greater than 9000, and verify the proof in a Solana program.
---

In this tutorial you'll prove that you know a number greater than 9000 without revealing it, and
check that proof in a Solana program.

The claim is a comparison, and comparisons are the first thing a circuit can't do natively. A
circuit computes in a prime field, which has no "less than", so to compare numbers it first proves
they're small: it splits each into bits and checks every bit. That's a **range proof**, and it sits
under every age, balance and price check you'll write. Over 9000 is the smallest one there is.

By the end you'll have built the whole xark loop:

- a **circuit**: four lines of Rust that state the rule;
- its **tests**, run with `xark test`;
- **keys**, and a proof from the command line;
- a **Solana program** that verifies the proof, with the verifier crate and TypeScript client xark
  generates for it;
- an **end-to-end test** that proves in TypeScript, sends the proof to the program and sees it
  accepted.

<Callout title="Prerequisites">
- Stable Rust **1.89 or newer** ([rustup](https://rustup.rs)).
- The xark CLI: `cargo install xark-cli --version 0.4.0 --locked`.
- Node **22 or newer**, with npm.
- The [Anza CLI](https://docs.anza.xyz/cli/install), for `cargo-build-sbf`. This tutorial was run
  with `cargo-build-sbf` 4.1.0.

`xark doctor` checks the Rust and xark side.
</Callout>

Everything goes in one xark project, which you'll create in the first step. By the end it holds:

```text
over-9000/
├── circuits/over-9000/   the circuit crate
├── programs/over-9000/   the Solana program
├── clients/over-9000/    generated by xark: the Rust verifier crate and the TypeScript client
├── keys/over-9000/       the proving and verifying keys
└── tests/                the end-to-end test
```

<Steps>

<Step>
### Create the project

```sh
xark init over-9000 && cd over-9000
```

`xark init` makes a project: a `xark.toml`, one Cargo workspace for everything in it, and a circuit
crate in `circuits/over-9000/` that depends on `xark = "0.4"`. Its `src/lib.rs` holds a sample
circuit named after the project, `over_9000`. You'll replace it. Every command from here on runs at
the project's root. The [Projects](/docs/guides/projects) guide describes the layout.
</Step>

<Step>
### Write the rule

Replace `circuits/over-9000/src/lib.rs` with:

```rust title="circuits/over-9000/src/lib.rs"
use xark::prelude::*;

#[circuit]
pub fn over_9000(power_level: Private<u64>) {
    require(power_level > 9000u64);
}
```

That's the whole circuit. `Private` means the prover supplies `power_level` but the proof never
reveals it. `require` states what must hold: if it doesn't, there is no proof to make.

The `u64` is the range proof. Declaring `power_level` a `u64` makes xark split it into 64 bits and
constrain each to 0 or 1, which proves it lies in `[0, 2^64)`. With both sides that small, the
comparison can't wrap, and `>` means what it says. [Range proofs](/docs/learn-zk/range-proofs)
explains why, step by step. Pick a type and a value to see the bits a value is checked against:

<IntegerWidths />

`9000` is a literal, so it's fixed into the circuit. The circuit has no public inputs at all.
</Step>

<Step>
### Add tests

Append two tests to the same file:

```rust title="circuits/over-9000/src/lib.rs"
#[cfg(test)]
mod tests {
    use super::over_9000;

    #[test]
    fn accepts_a_value_over_9000() {
        over_9000(9001).unwrap();
    }

    #[test]
    fn rejects_the_boundary() {
        assert!(over_9000(9000).is_err());
    }
}
```

`#[circuit]` lets a test call the circuit like a function. It returns `Ok` when the inputs satisfy
every constraint. The second test is as important as the first: it checks that the circuit
refuses what it should.
</Step>

<Step>
### Run the tests

```console
$ xark test
xark building circuit `over-9000`
xark 129 vars, 131 constraints, 128 witness-gen ops
xark circuit digest 4816ee24881c12772e0ef0b08f3c8578
...
running 2 tests
test tests::rejects_the_boundary ... ok
test tests::accepts_a_value_over_9000 ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

The first run compiles xark and takes a little while. 128 of the 131 constraints are range checks,
one per bit: 64 for `power_level`, and 64 for the difference between it and 9000, whose top bit
says which side is bigger. Two more belong to the comparison itself, and one is the `require`.
`xark profile` breaks them down by source line. The digest is the circuit's fingerprint: you'll get
the same one. For more on writing tests, see [Test a circuit](/docs/guides/testing).
</Step>

<Step>
### Make the keys and a first proof

```console
$ xark setup
R1CS form: reduced (minimize saves 0.0% rows, 0.0% variables)
...
Key: a single-party setup from OS randomness: sound unless whoever ran `xark setup` kept that randomness (xark doesn't). `xark ceremony` spreads that trust.
```

This writes the proving key `pk.bin` and the verifying key `vk.bin` to `keys/over-9000/`. Both keys
belong in version control: the program you'll write embeds the verifying key. Now prove that 9001
is over 9000:

```console
$ xark prove --inputs '{"power_level": 9001}'
...
✅ Proof produced and self-checked (0 public input(s)).
   solved in 0.00s, proved in 0.00s
```

And try 9000:

```console
$ xark prove --inputs '{"power_level": 9000}'
error: witness does not satisfy the circuit

  circuits/over-9000/src/lib.rs:5:5  require(power_level > 9000u64);

  constraint #130 does not hold
  form  (⟨1 wire⟩) · (1) = 0
```

There's no proof of a false statement. xark names the line that fails.
</Step>

<Step>
### Add a program

```console
$ xark add program over-9000
...
Generated verifier crate `over-9000-verifier` at .../clients/over-9000/rust (0 public input(s), VK = 512 B). Depend on it from your Solana program and call `verify(&proof, PublicInputs { .. })`.
...
✅ TypeScript client for `over_9000` at .../clients/over-9000/ts/over_9000.ts

xark added program `over-9000-program` in .../programs/over-9000, verifying `over-9000`
```

One command writes everything around the circuit:

- `clients/over-9000/rust/`, the **verifier crate** `over-9000-verifier`. It has the verifying key
  built in, and the proof of 9001 you just made bundled as its self-test.
  [How verification works](/docs/guides/how-verification-works) explains what it checks and how.
- `clients/over-9000/ts/over_9000.ts`, the **TypeScript client**. It types the circuit's inputs:
  `power_level: Private<u64>` becomes `powerLevel: U64`. The
  [TypeScript clients](/docs/guides/typescript-clients) guide covers what else it holds.
- `programs/over-9000/`, a **Pinocchio program**, the crate `over-9000-program`, that depends on
  the verifier crate.
- `tests/over-9000.test.ts`, a **LiteSVM test**, with the `package.json` that runs it.

Both clients are generated from the circuit, and `xark build` regenerates them whenever it changes.
The program and the test are yours to edit, and you'll replace both.
</Step>

<Step>
### Write the Solana program

The generated program reads a proof and its public inputs from the instruction data. This circuit
has no public inputs, so you'll write one that takes only the proof, in a single file. Remove the
generated modules:

```sh
rm -r programs/over-9000/src/errors.rs programs/over-9000/src/instructions
```

`programs/over-9000/Cargo.toml` already depends on the verifier crate and Pinocchio:

```toml title="programs/over-9000/Cargo.toml"
[dependencies]
over-9000-verifier = { path = "../../clients/over-9000/rust" }
pinocchio = "0.11"
```

A Pinocchio program has the same shape at any size: an entrypoint that hands the instruction to
a struct, which parses and checks its input and then does the work, and an enum for the errors the
program adds to the built-in ones. This program has one instruction, `Verify`, and takes no
accounts, so it all fits in `lib.rs`. Replace `programs/over-9000/src/lib.rs` with the entrypoint:

```rust title="programs/over-9000/src/lib.rs"
#![cfg_attr(not(test), no_std)]

use over_9000_verifier::{Proof, verify};
use pinocchio::{
    AccountView, Address, ProgramResult,
    error::{ProgramError, ToStr},
    program_entrypoint,
};

program_entrypoint!(process_instruction);
#[cfg(not(test))]
pinocchio::nostd_panic_handler!();
#[cfg(not(test))]
pinocchio::no_allocator!();

fn process_instruction(
    _program_id: &Address,
    _accounts: &mut [AccountView],
    instruction_data: &[u8],
) -> ProgramResult {
    let result = Verify::try_from(instruction_data).and_then(|verify| verify.process());
    // The program's own errors log their names, which the client tests match.
    if let Err(error @ ProgramError::Custom(_)) = &result {
        log(error.to_str::<Over9000Error>());
    }
    result
}

/// `Program log: <message>`.
fn log(message: &str) {
    #[cfg(any(target_os = "solana", target_arch = "bpf"))]
    // SAFETY: the pointer and length are a valid `&str`'s.
    unsafe {
        pinocchio::syscalls::sol_log_(message.as_ptr(), message.len() as u64)
    };
    #[cfg(not(any(target_os = "solana", target_arch = "bpf")))]
    let _ = message;
}
```

The entrypoint only dispatches. With one instruction there's no discriminator byte to match on:
all of the instruction data is the proof. When the program fails with one of its own errors, it
logs the error's name, so a client sees `InvalidProof` rather than a bare number. The
`cfg(not(test))` lines leave out the panic handler and allocator when `xark test` runs the
program's Rust tests on your machine.

Add the instruction data, parsed to its exact length:

```rust title="programs/over-9000/src/lib.rs"
pub struct VerifyInstructionData<'a> {
    pub proof: &'a [u8; 256],
}

impl<'a> TryFrom<&'a [u8]> for VerifyInstructionData<'a> {
    type Error = ProgramError;

    fn try_from(data: &'a [u8]) -> Result<Self, Self::Error> {
        // The proof and nothing else: a byte more or less is not this instruction.
        let proof = data
            .try_into()
            .map_err(|_| ProgramError::InvalidInstructionData)?;
        Ok(Self { proof })
    }
}
```

Converting to a `[u8; 256]` is the length check. A byte more or less fails with the built-in
`InvalidInstructionData` before anything is verified, so the program never reads a proof out of the
wrong bytes.

Add the instruction, which verifies the proof:

```rust title="programs/over-9000/src/lib.rs"
pub struct Verify<'a> {
    pub data: VerifyInstructionData<'a>,
}

impl<'a> TryFrom<&'a [u8]> for Verify<'a> {
    type Error = ProgramError;

    fn try_from(data: &'a [u8]) -> Result<Self, Self::Error> {
        Ok(Self {
            data: VerifyInstructionData::try_from(data)?,
        })
    }
}

impl Verify<'_> {
    // Out of line: inlined into the entrypoint under fat LTO, the pairing check's
    // buffers took its frame past the SBF limit of 4 KiB, which only warns at build
    // time and corrupts the stack at run time.
    #[inline(never)]
    pub fn process(&self) -> ProgramResult {
        if !verify(&Proof::from_le_bytes(self.data.proof), []) {
            return Err(Over9000Error::InvalidProof.into());
        }
        Ok(())
    }
}
```

`verify` is the check that matters: it refuses any proof not made with this circuit's proving key
from inputs that satisfy it, so nobody gets past it without knowing a number over 9000. Its second
argument is the circuit's public inputs. The crate generates a `PublicInputs` struct with them as
named fields and packs them into field elements for you; this circuit has none, so the struct is
empty and `[]`, no field elements, says the same thing. Their number is checked when the program
compiles.

Last, add the program's error:

```rust title="programs/over-9000/src/lib.rs"
#[repr(u32)]
pub enum Over9000Error {
    InvalidProof = 0,
}

impl From<Over9000Error> for ProgramError {
    fn from(e: Over9000Error) -> Self {
        ProgramError::Custom(e as u32)
    }
}

impl TryFrom<u32> for Over9000Error {
    type Error = ProgramError;

    fn try_from(code: u32) -> Result<Self, Self::Error> {
        match code {
            0 => Ok(Self::InvalidProof),
            _ => Err(ProgramError::InvalidArgument),
        }
    }
}

impl ToStr for Over9000Error {
    fn to_str(&self) -> &'static str {
        match self {
            Self::InvalidProof => "InvalidProof: invalid proof",
        }
    }
}
```

A proof that doesn't verify has no built-in `ProgramError`, so it gets one of the program's own.
The codes number from 0, and `ToStr` gives each the name the entrypoint logs. A bad length already
had a built-in error, so it uses that.
</Step>

`xark build` builds the circuit and regenerates its clients when they're out of date (here they

program. The program is at `target/deploy/over_9000_program.so`. An additional benefit of

whereas `cargo build-sbf` only warns about it.

<Step>
### Prove and verify onchain

The test proves with the generated client, then sends the proof to the program in
[LiteSVM](https://github.com/LiteSVM/litesvm), an in-process Solana VM with the same `alt_bn128`
syscalls as mainnet, and no validator or network. Replace `tests/over-9000.test.ts` with:

```ts title="tests/over-9000.test.ts"
// Prove "over 9000" with the generated client, then verify it onchain.
// The instruction data is the proof, which is 256 bytes.
import { generateKeyPairSigner, type Address, type Instruction } from "@solana/kit";
import { circuit, funded, program as deployed, send, vm } from "@blueshift-gg/xark/testing";
import { CheckFailed, Over9000, type Over9000Prover } from "../clients/over-9000/ts/over_9000";

let programAddress: Address;
let prover: Over9000Prover;

beforeAll(async () => {
  programAddress = (await generateKeyPairSigner()).address; // the program takes any address
  // Pinned to the circuit this client was generated from: a deployment can't swap it.
  prover = await Over9000.prover(circuit("over-9000"), { digest: Over9000.digest });
});

const verify = (data: Uint8Array): Instruction => ({ programAddress, data });

test("a proof of 9001 verifies onchain", async () => {
  const proof = prover.prove({ powerLevel: 9001 });
  const svm = vm({ [programAddress]: deployed("over-9000") });
  const payer = await funded(svm);

  await send(svm, payer, verify(proof.toBytes()));

  const tampered = proof.toBytes();
  tampered[0] ^= 1;
  await expect(send(svm, payer, verify(tampered))).rejects.toThrow(/InvalidProof/);
  // A truncated proof is invalid
  await expect(send(svm, payer, verify(proof.toBytes().slice(1)))).rejects.toThrow(/invalid instruction data/);
});

test("9000 has no proof", () => {
  // The prover names the check that fails, from the circuit's source.
  expect(() => prover.prove({ powerLevel: 9000 })).toThrow(CheckFailed);
  expect(() => prover.prove({ powerLevel: 9000 })).toThrow(/power_level > 9000/);
});
```

`@blueshift-gg/xark/testing` finds the project's build output: `circuit("over-9000")` is the
circuit and its keys, `deployed("over-9000")` the program's `.so` ELF file. `vm` starts a LiteSVM with the
program at an address the test makes up, `funded` makes a payer, and `send` signs and sends a
transaction, throwing with the program's logs when it fails. `{ digest: Over9000.digest }` pins the
prover to the circuit this client was generated from, so a different circuit file is refused.

A proof is always 256 bytes, and `toBytes()` is exactly what the program reads. `verify` refuses to Any sort of tempering —
flipping one of its bits, or truncating it — must
it must make `verify` refuse it, and a proof one byte short must fail the length check first. When
inputs fail, the client throws a `CheckFailed` that names the same source line `xark prove` did:
``the inputs fail the check at src/lib.rs:5:5: `require(power_level > 9000u64);` ``.

</Step>

## What you built

A secret number went into a TypeScript prover, and a 256-byte proof came out. A Solana program
checked it and learned only that the number is over 9000. The proof rests on a range proof:
64 constrained bits that make `power_level` an integer, so `>` could be trusted. Along the way you
used each part of xark: `xark test` for the circuit, `xark setup` and `xark prove` for keys and
proofs, `xark add program` for the program and its clients, and `xark build` for all of it.

When you change the circuit, run `xark build`. It makes new keys for the changed circuit,
regenerates the verifier crate and the client, and rebuilds the program: the client and verifier
follow the circuit. Commit `keys/` and `clients/` with it.

The proof says someone knows *a* number over 9000. It doesn't tie that number to anything: anyone
can pick 9001. The next tutorial, zKYC, binds hidden values to a published commitment, and the
same range proofs check an age and a net worth.

<Callout type="warn" title="Before you deploy">
`xark setup` made a single-party key: sound unless whoever ran it kept its randomness. A program
that guards value needs a key from a ceremony. See [The trusted setup](/docs/trust/trusted-setup).
</Callout>
