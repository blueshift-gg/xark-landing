---
title: "01 · Over 9000"
description: Your first range proof. Prove a secret number is greater than 9000, and verify the proof in a Solana program.
---

In this tutorial you'll prove that you know a number greater than 9000 without revealing it, and
check that proof in a Solana program.

The claim is a comparison, and comparisons are the first thing a circuit can't do natively. A
circuit computes in a prime field, which has no "less than", so to compare numbers it first proves
they're small: it splits each into bits and checks every bit. That's a **range proof**, and it sits
under every age, balance and price check you'll write. Over 9000 is the smallest one there is.

By the end you'll have built the whole xark loop by hand:

- a **circuit**: four lines of Rust that state the rule;
- its **tests**, run with `xark test`;
- **keys**, and a proof from the command line;
- a **TypeScript client** that proves in Node;
- a **Solana program** that verifies the proof;
- an **end-to-end test** that sends the proof to the program and sees it accepted.

<Callout title="Prerequisites">
- Stable Rust **1.89 or newer** ([rustup](https://rustup.rs)).
- The xark CLI 0.3: `cargo install xark-cli`.
- Node **22 or newer**, with npm.
- The [Anza CLI](https://docs.anza.xyz/cli/install), for `cargo-build-sbf`. This tutorial was run
  with `cargo-build-sbf` 4.1.0.

`xark doctor` checks the Rust and xark side.
</Callout>

Everything goes in one directory, with a folder per part:

```text
xark-tutorial/
├── over-9000/   the circuit crate
├── program/     the Solana program
└── app/         the TypeScript client and the end-to-end test
```

<Steps>

<Step>
### Create the circuit crate

```sh
mkdir xark-tutorial && cd xark-tutorial
xark init over-9000
```

`xark init` writes a circuit crate that depends on `xark = "0.3"`. Its `src/lib.rs` holds a
sample circuit named after the crate, `over_9000`. You'll replace it.
</Step>

<Step>
### Write the rule

Replace `over-9000/src/lib.rs` with:

```rust title="over-9000/src/lib.rs"
use xark::prelude::*;

#[circuit]
pub fn over_9000(power_level: Private<u64>) {
    require(power_level > 9000u64);
}
```

That's the whole circuit. `Private` means the prover supplies `power_level` but the proof never
reveals it. `require` states what must hold: if it doesn't, there is no proof to make.

The `u64` is the range proof. Declaring `power_level` a `u64` makes xark split it into 64 bits and
constrain each to 0 or 1, which proves it lies in `[0, 2^64)`. With both sides that small, the
comparison can't wrap, and `>` means what it says. [Range proofs](/docs/learn-zk/range-proofs)
explains why, step by step. Pick a type and a value to see the bits a value is checked against:

<IntegerWidths />

`9000` is a literal, so it's fixed into the circuit. The circuit has no public inputs at all.
</Step>

<Step>
### Add tests

Append two tests to the same file:

```rust title="over-9000/src/lib.rs"
#[cfg(test)]
mod tests {
    use super::over_9000;

    #[test]
    fn accepts_a_value_over_9000() {
        over_9000(9001).unwrap();
    }

    #[test]
    fn rejects_the_boundary() {
        assert!(over_9000(9000).is_err());
    }
}
```

`#[circuit]` lets a test call the circuit like a function. It returns `Ok` when the inputs satisfy
every constraint. The second test is as important as the first: it checks that the circuit
refuses what it should.
</Step>

<Step>
### Run the tests

```console
$ xark test over-9000
xark building circuit `over-9000`
xark 129 vars, 131 constraints, 128 witness-gen ops
xark circuit digest 4816ee24881c12772e0ef0b08f3c8578
...
running 2 tests
test tests::rejects_the_boundary ... ok
test tests::accepts_a_value_over_9000 ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

The first run compiles xark and takes a little while. 128 of the 131 constraints are range checks,
one per bit: 64 for `power_level`, and 64 for the difference between it and 9000, whose top bit
says which side is bigger. Two more belong to the comparison itself, and one is the `require`.
`xark profile over-9000` breaks them down by source line. The digest is the circuit's fingerprint: you'll get
the same one. For more on writing tests, see [Test a circuit](/docs/guides/testing).
</Step>

<Step>
### Make the keys and a first proof

```console
$ xark setup over-9000
R1CS form: reduced (minimize saves 0.0% rows, 0.0% variables)
...
Key: a single-party setup from OS randomness: sound unless whoever ran `xark setup` kept that randomness (xark doesn't). `xark ceremony` spreads that trust.
```

This writes the proving key `pk.bin` and the verifying key `vk.bin` to
`over-9000/target/xark/over-9000/`. Now prove that 9001 is over 9000:

```console
$ xark prove over-9000 --inputs '{"power_level": 9001}'
...
✅ Proof produced and self-checked (0 public input(s)).
```

And try 9000:

```console
$ xark prove over-9000 --inputs '{"power_level": 9000}'
error: witness does not satisfy the circuit

  src/lib.rs:5:5  require(power_level > 9000u64);
```

There's no proof of a false statement. xark names the line that fails.
</Step>

<Step>
### Generate the TypeScript client

```console
$ xark client over-9000 --out app/
✅ TypeScript client for `over_9000` at app/over_9000.ts
```

`app/over_9000.ts` types the circuit's inputs: `power_level: Private<u64>` becomes
`powerLevel: U64`. Set up a Node project around it, with the xark runtime and a test runner:

```sh
cd app
npm init -y
npm pkg set type=module
npm install @blueshift-gg/xark@^0.3.0 vitest
```

The [TypeScript clients](/docs/guides/typescript-clients) guide covers what else the generated
file holds.
</Step>

<Step>
### Prove from TypeScript

Create `app/over-9000.test.ts`:

```ts title="app/over-9000.test.ts"
import { readFileSync } from "node:fs";
import { beforeAll, expect, test } from "vitest";
import { CheckFailed, Over9000, type Over9000Prover } from "./over_9000";

// What `xark build` and `xark setup` wrote. A web app would serve this
// directory and pass its URL instead.
const out = "../over-9000/target/xark/over-9000/";
const read = (file: string) => new Uint8Array(readFileSync(out + file));

let prover: Over9000Prover;
beforeAll(async () => {
  prover = await Over9000.prover(
    { circuit: read("circuit.xbc"), provingKey: read("pk.bin"), sources: readFileSync(out + "sources.json", "utf8") },
    { digest: Over9000.digest },
  );
});

test("a proof of 9001 verifies", async () => {
  const proof = prover.prove({ powerLevel: 9001 });
  expect(proof.toBytes().length).toBe(256);

  const verifier = await Over9000.verifier(read("vk.bin"));
  expect(verifier.verify(proof).toBe(true);
});

test("9000 has no proof", () => {
  expect(() => prover.prove({ powerLevel: 9000 })).toThrow(CheckFailed);
  expect(() => prover.prove({ powerLevel: 9000 })).toThrow(/power_level > 9000/);
});
```

`{ digest: Over9000.digest }` pins the prover to the circuit this client was generated from, so a
different circuit file is refused.

Run it from `app/`:

```console
$ npx vitest run --reporter=verbose
 ✓ over-9000.test.ts > a proof of 9001 verifies 52ms
 ✓ over-9000.test.ts > 9000 has no proof 47ms

 Test Files  1 passed (1)
      Tests  2 passed (2)
```

A proof is always 256 bytes. When inputs fail, the client throws a `CheckFailed` that names the
same source line `xark prove` did: ``the inputs fail the check at src/lib.rs:5:5: `require(power_level > 9000u64);` ``.
</Step>

<Step>
### Write the Solana program

```sh
cargo new --lib program --name over-9000-program
```

Replace `program/Cargo.toml` with:

```toml title="program/Cargo.toml"
[package]
name = "over-9000-program"
version = "0.1.0"
edition = "2024"

[lib]
crate-type = ["cdylib"]

[dependencies]
over-9000-verifier = { path = "../over-9000/over-9000-verifier" }
pinocchio = "0.11"
```

A Pinocchio program has the same shape at any size: an entrypoint that hands the instruction to
a struct, which parses and checks its input and then does the work, and an enum for the errors the
program adds to the built-in ones. This program has one instruction, `Verify`, and takes no
accounts, so it all fits in `lib.rs`. Replace `program/src/lib.rs` with the entrypoint:

```rust title="program/src/lib.rs"
#![no_std]
use over_9000_verifier::{Proof, verify};
use pinocchio::{AccountView, Address, ProgramResult, error::ProgramError, program_entrypoint};

program_entrypoint!(process_instruction);
pinocchio::nostd_panic_handler!();
pinocchio::no_allocator!();

fn process_instruction(_program_id: &Address, _accounts: &mut [AccountView], instruction_data: &[u8]) -> ProgramResult {
    Verify::try_from(instruction_data)?.process()
}
```

The entrypoint only dispatches. With one instruction there's no discriminator byte to match on:
all of the instruction data is the proof.

Add the instruction data, parsed to its exact length:

```rust title="program/src/lib.rs"
pub struct VerifyInstructionData<'a> {
    pub proof: &'a [u8; 256],
}

impl<'a> TryFrom<&'a [u8]> for VerifyInstructionData<'a> {
    type Error = ProgramError;

    fn try_from(data: &'a [u8]) -> Result<Self, Self::Error> {
        // The proof and nothing else: the circuit has no public inputs.
        let proof = data.try_into().map_err(|_| ProgramError::InvalidInstructionData)?;
        Ok(Self { proof })
    }
}
```

Converting to a `[u8; 256]` is the length check. A byte more or less fails with the built-in
`InvalidInstructionData` before anything is verified, so the program never reads a proof out of the
wrong bytes.

Add the instruction, which verifies the proof:

```rust title="program/src/lib.rs"
pub struct Verify<'a> {
    pub data: VerifyInstructionData<'a>,
}

impl<'a> TryFrom<&'a [u8]> for Verify<'a> {
    type Error = ProgramError;

    fn try_from(data: &'a [u8]) -> Result<Self, Self::Error> {
        Ok(Self { data: VerifyInstructionData::try_from(data)? })
    }
}

impl Verify<'_> {
    pub fn process(&self) -> ProgramResult {
        if !verify(&Proof::from_le_bytes(self.data.proof), &[]) {
            return Err(Over9000Error::InvalidProof.into());
        }
        Ok(())
    }
}
```

`verify` is the check that matters: it refuses any proof not made with this circuit's proving key
from inputs that satisfy it, so nobody gets past it without knowing a number over 9000. It takes
the public inputs as an array of 32-byte values, one per input, so their number is checked when the
program compiles. This circuit has none, so it's `&[]`.

Last, add the program's error:

```rust title="program/src/lib.rs"
#[repr(u32)]
pub enum Over9000Error {
    InvalidProof = 0,
}

impl From<Over9000Error> for ProgramError {
    fn from(e: Over9000Error) -> Self {
        ProgramError::Custom(e as u32)
    }
}
```

A proof that doesn't verify has no built-in `ProgramError`, so it gets one of the program's own.
The codes number from 0, and a client sees this one as `custom program error: 0x0`. A bad length
already had a built-in error, so it uses that.
</Step>

<Step>
### Verify the proof onchain

The last test sends the proof to the program in [LiteSVM](https://github.com/LiteSVM/litesvm),
an in-process Solana VM with the same `alt_bn128` syscalls as mainnet, and no validator or
network. Back in `app/`, add the Solana packages:

```sh
cd ../app
npm install @solana/kit litesvm
```

Add these imports at the top of `over-9000.test.ts`:

```ts title="app/over-9000.test.ts"
import {
  appendTransactionMessageInstruction, createTransactionMessage, generateKeyPairSigner, lamports, pipe,
  setTransactionMessageFeePayerSigner, setTransactionMessageLifetimeUsingBlockhash, signTransactionMessageWithSigners,
  type Address, type KeyPairSigner,
} from "@solana/kit";
import { FailedTransactionMetadata, LiteSVM } from "litesvm";
```

and this at the end:

```ts title="app/over-9000.test.ts"
// Send `data` to `program` in one transaction, paid by `payer`. Returns the
// compute units it used, or throws with the program's logs.
async function send(svm: LiteSVM, payer: KeyPairSigner, program: Address, data: Uint8Array) {
  const tx = await pipe(
    createTransactionMessage({ version: 0 }),
    (m) => setTransactionMessageFeePayerSigner(payer, m),
    (m) => setTransactionMessageLifetimeUsingBlockhash({ blockhash: svm.latestBlockhash(), lastValidBlockHeight: 0n }, m),
    (m) => appendTransactionMessageInstruction({ programAddress: program, data }, m),
    (m) => signTransactionMessageWithSigners(m),
  );
  const result = svm.sendTransaction(tx);
  svm.expireBlockhash();
  if (result instanceof FailedTransactionMetadata) {
    throw new Error(`transaction failed: ${result.err()}\n${result.meta().logs().join("\n")}`);
  }
  return result.computeUnitsConsumed();
}

test("the program accepts the proof, and only the proof", async () => {
  const svm = new LiteSVM();
  const program = (await generateKeyPairSigner()).address;
  svm.addProgramFromFile(program, "../program/target/deploy/over_9000_program.so");
  const payer = await generateKeyPairSigner();
  svm.airdrop(payer.address, lamports(1_000_000_000n));

  const proof = prover.prove({ powerLevel: 9001 }).toBytes();
  const units = await send(svm, payer, program, proof);
  console.log(`verified onchain in ${units} CU`);

  // One flipped bit: Over9000Error::InvalidProof, the program's error 0.
  const tampered = proof.slice();
  tampered[0] ^= 1;
  await expect(send(svm, payer, program, tampered)).rejects.toThrow(/custom program error: 0x0/);

  // One byte short: not a proof at all.
  await expect(send(svm, payer, program, proof.slice(1))).rejects.toThrow(/invalid instruction data/);
});
```

The program takes any address, so the test makes one up. Flipping one bit of the proof must make
`verify` refuse it, and a proof one byte short must fail the length check first. Run the tests:

```console
$ npx vitest run --reporter=verbose
 ✓ over-9000.test.ts > a proof of 9001 verifies 52ms
 ✓ over-9000.test.ts > 9000 has no proof 47ms
stdout | over-9000.test.ts > the program accepts the proof, and only the proof
verified onchain in 75949 CU

 ✓ over-9000.test.ts > the program accepts the proof, and only the proof 40ms

 Test Files  1 passed (1)
      Tests  3 passed (3)
```

Your proof was verified onchain, in about 76,000 compute units, and the tampered and truncated
ones were refused.
</Step>

</Steps>

## What you built

A secret number went into a TypeScript prover, and a 256-byte proof came out. A Solana program
checked it and learned only that the number is over 9000. The proof rests on a range proof:
64 constrained bits that make `power_level` an integer, so `>` could be trusted. Along the way you used each part of
xark: `xark test` for the circuit, `xark setup` and `xark prove` for keys and proofs, `xark client`
for the app, and `xark export` for the program.

When you change the circuit, rerun `xark setup`, `xark prove`, `xark export` and `xark client`,
then rebuild the program. The client and verifier follow the circuit.

The proof says someone knows *a* number over 9000. It doesn't tie that number to anything: anyone
can pick 9001. The next tutorial, zKYC, binds hidden values to a published commitment, and the
same range proofs check an age and a net worth.

<Callout type="warn" title="Before you deploy">
`xark setup` made a single-party key: sound unless whoever ran it kept its randomness. A program
that guards value needs a key from a ceremony. See [The trusted setup](/docs/trust/trusted-setup).
</Callout>

[01-over-9000](https://github.com/blueshift-gg/xark-examples/tree/main/01-over-9000) in
xark-examples.
